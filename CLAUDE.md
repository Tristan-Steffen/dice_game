# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Fumble** — a Balatro-like 3D dice roguelike built in **Godot 4.7** (`gl_compatibility` renderer, Jolt physics). Code comments and in-game text are in **German**; identifiers are a mix. The whole game plays on a single table surface at world **Y = 0**, viewed as a "casino table screen": 2D UI is rendered into a `SubViewport` and displayed on a mesh (see Architecture). The table has **no edge**: the felt runs on as an endless floor that fades into the dark room (`TableGround`), leaving space for future features around the play area.

**Comments:** keep them to the necessary minimum — short German one-liners that state a non-obvious rule, constraint, or design decision. Don't restate what the code already says, don't duplicate a `description` string that sits one line below, and don't write essay-length narrative blocks or "siehe X" cross-reference chains. When in doubt, cut it.

## Architecture

### Layered `scripts/` — the folder IS the dependency rule
`core/` and `data/` must not import from folders below them. New scripts are placed by layer, not by feature:

- **`data/`** — `Resource` records only: `DieDefinition` (per-die faces/materials/rifts + the innate `essence_id`), `Charm`, `Engraving`, `Pack` (sealed shop goods), `DieMaterial`, `Essence`, `Rift`, `RoundEvent` (per-block round events). Each type's ids are `const` string constants (single source of truth) so a typo is a compile error, not a silent no-op that never matches in a `match`. The layer rule bites here: `Rift.tint` **mirrors the `CasinoStyle.CHARGE` literal** instead of importing it (data/ never reaches into ui/), and a test asserts the two stay equal so drift fails loudly.
- **`core/`** — pure logic, **no Nodes** (all `RefCounted`/static): `DiceScoring` (Balatro-style hand values = base points × multiplier), `CharmEffects`/`EtchingEffects`/`MaterialEffects`/`EssenceEffects`/`RiftEffects` (id-dispatched effect resolution), `GameRun` (the persistent run state — money, 30-die pool, charms, engravings, sealed packs, round progress; owns all economy methods and emits signals to the UI. Charms are hard-capped at `CHARM_CAPACITY` (6, the table's `CharmRowView.SPOT_COUNT`): `_grant_charm` refuses when `charms_full()`, `purchase_charm` therefore checks **before** paying, and the shop/Schwarzmarkt charm cards lock themselves instead of queueing an invisible seventh charm), `ScoreBreakdown`, `SlotMachine`, `SideBet` (the Nebenwetten catalog: every template carries an `unlock` hub level, so the shelf grows with the casino — `roll_offers(count, hub_level, benchmark)` filters the pool *before* shuffling. Point targets are not authored, they are **scaled**: a `target_factor` times the **stored** `run.round_goal`, rounded by `_nice_target` and **frozen into the offer** at roll time — deliberately not `effective_goal()`, so a benchmark clause signed after the betting window can never move a number already printed on a button. Two stake kinds cost **nothing at placement** and bill per taken hand/die instead (`MONEY_PER_HAND`/`MONEY_PER_DIE`, collected by `GameRun.tax_side_bets` next to the clause fee in the take); if the money no longer covers the bill the bet is `voided` — it stops taxing and loses, which is the whole risk of a tax bet. The Turniernacht factor doubles money, engravings and ⚡ but never a unique good (Sonderposten, Paket, Chipstufe)), `DiceOffer` (dice templates + refinement rolls, shared with `Pack`), `GameSettings` (volume/fullscreen in `user://settings.cfg` — the view reports changes, `scene_root` applies and saves them).
- **`dice/`** — the physical die: `DiceController` (physics of the 6 dice slots — throw/hold/rest-detection; which value shows comes from each slot's `DieDefinition`, physics only reports which physical face is up), `DieBuilder` (builds dice entirely in code — no `.tscn`), `DieFaceDisplay` (also owns the **pointing** at a die: `pick_face`/`edge_distance` project the face and edge midpoints to the screen and take the nearest facing one — no physics ray, because the ceremony dice carry no collision shape), `StasisEmitter` (puck + iris + beam under a floating die; the trays hang one under every slot), `FloatingDie` (a real die hovering in such a field — see *A die is never shown twice*).
- **`table/`** — 3D props, camera, and the on-table screen system (see below).
- **`ui/`** — 2D panels and styling shown inside the table screen (`ShopController`, `TitleView` (title screen + pause menu), `WorkshopView` — the Werkstatt stash that opens packs and hosts `DieInspectorView` (the engraving station) via `attach_station` —, `SupplyDrawerView` (see below), `SlotBankView`, `SideBetPanel`, `CharmLibraryView`, `EngravingRenderer`, `CasinoStyle`, plus the shared builders `DiceRowView`/`CharmThumb`/`DiceGridView`/`DieNetView` — the last one is the "Würfelnetz" (unfolded-cross die dossier: cell color = face material, cell border = the essence glow, gold frame = face up, plus an Essenz-Chip — a tinted diamond in the empty top-left cross corner reporting the die's soul — and per broken face a crack polyline through the cell middle) shown in the pit's compact net card via `TableScreen.set_pit_die`; hovering a face/edge writes a single-line material caption to a separate wide bar lower in the pit screen — between the net card and the pit's bottom wall (`set_pit_net_hint`/`place_pit_net_hint`), never inside the card). That caption has ONE source, `DieNetView.hint_for(def, face)` (material + Stufe, Leiterbahn, rifts; the Essenz-Chip explains the soul) — the pack nets on the workbench write the same line into the bench's info bar, so a cell says the same thing wherever it is shown. **The net is the one way a die is ever shown flat** — pit card, the workbench's 30-die grid (`DiceGridView` detail tiles) and the engraving station's face summary all draw the same cross, because only a layout by *physical* face position can carry the Leiterbahn arrows. The station composes its own interactive chips into it via `cell_position`/`edge_chip`/`rift_cracks`/`level_badges`/`pointer_arrows` instead of calling `build`, so selection, dimming and preview survive; `DiceGridView.detail_tile_size` derives the tile from `net_size`, never a guessed constant. The eye total lives **inside** the net (`total_badge`, in the free top-right cross corner opposite the Essenz-Chip) rather than on a band above it — the 30 tiles share a fixed area, so a reclaimed strip becomes bigger cells. Consequence for the station: chips sit by physical index, so the by-value `face_order` no longer decides layout — it only decides build order.

### `scene_root.gd` — the single coordinator
Top-level `Node3D` (not in a subfolder). Owns exactly one `GameRun`, wires its signals to the UI, drives round flow (throw → score → take/reroll → round-goal → shop — and the **pit is the shop's second exit**: focusing it while `phase == SHOP` means "Fertig", so `_on_camera_mode_changed` calls `ShopController.close()` and `_on_shop_closed` only zooms back to the overview when the camera really stands in the hub, never yanking back a flight already under way), and passes the same `GameRun` instance (typed) to `ShopController` and `DieInspectorView`, which mutate state **only** through `GameRun` methods. It also does mouse-forwarding: `_forward_screen_mouse` projects window clicks onto the table plane and `push_input`s them into the `SubViewport`; `_screen_forwards_pixel` gates which rects forward per camera mode. `_ready` is split into named setup steps (`_setup_dice`/`_setup_table_screen`/`_setup_camera_targets`/`_setup_panels`/`_setup_settings_ui`); camera raycasts go through the shared `_ray_pick(pos, mask)` helper and click zones through `_add_click_zone`.

### The table-as-screen display system (`table/`)
- **`TableScreen`** (`table_screen.gd`) — a `SubViewport` rendering 2D UI to a `ViewportTexture` on the "Screen" mesh. Its windows live inside it: `HubView` (home page + `ShopController` as an attached page), `WorkshopView`, `SlotBankView`, `SideBetPanel`, `TreasureChestView`.
- **The title HUD** — `TitleView` is a hub page like the shop and carries the start screen, the pause menu **and the game-over screen** (`Card.GAME_OVER`; `_home_card` is where `go_back()` lands, so after a loss the way back ends at the result, not at the menu). `CameraRig.Mode.TITLE` frames it: straight down (`TITLE_BASIS`, no tilt) at the distance that fits the whole hub window plus a margin (`title_distance`, `TITLE_MARGIN`), so the table stays visible around the menu — deliberately not a cover crop. Reflections are switched off there (`ScreenReflection.set_enabled`) — mirrored dice ghosted over the menu. Page changes at the title go through `HubView.fade_page_in/out/fade_current_in` (fade out, then the page rule hands the surface over, then fade in) — a hard cut showed while the camera was still travelling. "Neues Spiel" passes `fade_page_out` an `on_hidden` callback and takes over the fade-in itself: rebuilding the run costs ~0.24 s of frame time, and it has to sit in the dark moment between the two fades, never inside a fade or under the pull-back. Boot runs the normal setup and starts the round, then opens the title over it; "Neues Spiel" resets and plays `reveal_table()` (the long pull-back). Escape/the hub's Menü entry toggles it (`_toggle_title`) and it stays put on the start screen.
- **Combo chips** — every combination stands as a physical 3D chip on the **felt** (`ComboChipView`, model `assets/models/chip.glb`), wired into the LED network at its pins; there is no window under them. In `socket_mode` the 2D `ComboCellView` draws **nothing at all** — it survives purely as the data record and pixel anchor (cell center = origin of the scoring comets, cell size = basis of the wiring geometry). `ComboChipView.pin_offsets_px` is the single source for where the pins sit in screen pixels — everything docking onto them (the LED stubs, the purchase comets) derives from it instead of re-deriving the projection. The chip's **lid carries the display**: name, Basispunkte, ×Mult and the level badge ("LVL n") sit as Label3Ds flat on a glass field, because the lid is the face the overview camera sees best. Heat (= level % 5 on the cool→cyan→amber→red ramp, white-hot from 25 — every 5th level is reserved for a future cooler mount) glows in the front band, while the lid glass stays deliberately dark and capped (`SCREEN_EMISSION_MAX`) so the text never washes out. Since the cell shows nothing, the Rampenlicht also lives on the chip (`set_spotlight` = golden breath, driven by `scene_root._set_spotlight_combo`), and so does the highlight of the rolled hand: `set_glow` pulls **package, pins and band** into gold (`HIGHLIGHT_*`), which is the only way the counting combination is findable among thirteen chips. The lid glass is deliberately excluded from that gold — tinting it, plus the bloom off the golden package, swallowed its own text. The cell stays the single data source: after any `set_score`/`set_level`, `scene_root._sync_combo_chip` copies its values onto the chip — never write chip text directly.
  Two traps the model imposes: `Pins` has no UVs and `Body`'s were shredded by the Blender booleans, so surface textures must be **triplanar**; and the 45° front band leans exactly on lid height, so it needs `BAND_SEAT_DROP` or its top edge z-fights the lid into a dashed line.
- **The shop's Sortiment-Sperre** — `ShopController.sortiment_locked` (toggled from a button in the shop header, next to the money; the footer is already width-bound on high hub levels). While it stands, `open()` rolls **nothing**: the existing `spreads` stay, including their `*_bought` flags and the page the player left on, so a locked shop is the same shop next round. Unlocking resumes the normal per-visit reroll. The flag lives in `ShopController` because the spreads already do — and it is cleared in the `run` setter, so a fresh run always gets a fresh shop. A hub upgrade mid-visit still re-rolls the current spread (`refresh_after_hub_upgrade`): the new slots have to become visible, and that outranks the lock.
- **The Chip-Schale is open** — the shop's bowl of single goods (mixed dice and engravings, plus the round Übertaktungs-Chips) follows the felt's rule, not the window's: **no panel under a physical thing**, exactly like the combo chips. Each single is still a `Button` (hover and click must keep working) but carries `StyleBoxEmpty` in every state — the good just *lies* there. A dice single is a **real tumbling die** (`DiceRowView.build_thumb(def, size, true)` → its `TumbleStage`, the same isolated-world pattern as every other die thumbnail, only rotating and rendering `UPDATE_WHEN_VISIBLE`); an engraving single is its **seal alone**. Nothing in the bowl prints a price — reaching for a piece is what reveals it: `_show_shop_tooltip(anchor, title, body, price, net_def)` is the single hover window for the whole shop, and for a die it carries the full dossier (the Würfelnetz, so materials, Stufen, rifts and the Essenz-Chip all come free). The price line's colour is the one affordability decision in the shop and lives in the pure `price_tint(price, money)` (gold payable, `CasinoStyle.RED` not). Grabbing shows as a brighten-and-swell on the content (`_lift_single`), since there is no frame left to highlight. **Bought singles vanish** on the next `_show_spread` instead of greying out — but their `*_bought` flags stay in the spread, so the Sortiment-Sperre still shows the same shop with the sold piece gone, and `single_*_buttons` keeps a `null` at every sold index so `_refresh_affordability` stays index-true. A bought die is **not** placed: it goes to `GameRun.pending_dice` (`stash_die`, run state, survives visits and rerolls) and waits on the dealer's shelf — a slim strip under the bowl in the same bare grammar, no price, since it is paid for. Clicking a stashed die opens the exchange picker, a `DiceGridView` overlay of the whole 30-die pool; `exchange_pending_die(pending, pool)` then **writes into the chosen pool entry** (`become`, never a swap) and emits `pool_changed` + `pending_dice_changed`. Nothing warns and nothing is blocked: the grid's nets already show materials, Stufen, rifts and the Essenz-Chip, and *that* is the informed consent — a confirm dialog would only be paper in front of it. Cancelling leaves both sides untouched.
- **Hub vs. Werkstatt** — the split is *buy vs. use*: the hub is the casino side (round/roadmap, money, license upgrades, shop — everything sealed), the Werkstatt is the player's workbench (opening packs, the engraving stock, applying engravings). Anything dice-shaped belongs at the workbench corner. **Editing dice is not bounded by the shop but by the signature**: `scene_root.round_committed` (reset in `_start_new_round`, set in `_on_route_chosen` — or, in a round without offers, by the first throw) is what closes the station, so the whole pre-commitment window of the new round is still bench time. `_dice_editing_locked()` = `round_committed and phase != Phase.SHOP` is the single arbiter, pushed on open **and** re-pushed via `_sync_editing_lock()` whenever the commitment flips. While the station is **closed**, hovering a physical tray die shows its Würfelnetz on the workbench screen (`WorkshopView.show_hover_net`/`clear_hover_net`, driven per frame from `scene_root._update_workshop_hover` because the pointer is on the table, not in the `SubViewport` — it picks through the *same* `DiceTrayView.SLOT_PICK_LAYER` mask as a tray click, so there is one hit path). The card is an overlay in the window's top-right corner, it loses to the station (Eine-Ansicht-Regel) and to leaving the workshop, and since defs are shared instances a `pool_changed` rebuilds it while it stands.

**Hub-Ausbau zahlt in Ware.** Every upgrade grants sealed packs into `owned_packs` (opened through the normal Werkstatt flow — no new UI): *every* level from 2 on gets one 3-die pack whose three choice-dice all carry a soul (`Pack.essence_guaranteed` → `DiceOffer.roll_essence(…, guaranteed)`, which skips the chance roll but keeps the unique/secret exclusions and falls back to a non-unique soul rather than shipping a soulless die). `GameRun.HUB_REWARD_PACKS` is the one data table for the extras on top (5 → Zahlen + Kombination, 10 → 2× Zahlen + 3× Kombination); unlisted levels get only the dice pack. Booked in `upgrade_hub` **before** the ceremony; `last_hub_reward_packs` remembers what was granted so the ceremony can show it. The ceremony (`scene_root._play_hub_reward_ceremony`, never awaited) reveals one seal per pack **type** over the hub center (`PackIconRenderer`, "×n" for multiples), then flies one `pack_delivery_comet` per pack down the laid hub→workshop ader and lets the **last arrival** fire `celebrate_workshop_delivery`. Purely visual — book first, fly afterwards.
- **The workbench corner** — pool/discard trays on top, `WorkshopView` below them, and a row of three `SupplyDrawerView` windows under that, one per engraving category and colored like the matching shop pack. The drawers are **dual-mode on the same slots**: stock display normally, the engraving station's tool board while it's open (`set_ceremony`) — hence a fixed slot geography where unowned archetypes stay as shadows. A fourth drawer, the **Sonderbestand** (`SupplyDrawerView.CATEGORY_SPECIAL`, a pseudo-category), stands as a slim bench-height vitrine RIGHT of the workshop (`place_special_stock`, horizontal LED ader out of the bench side): it holds the one-off specials in `Engraving.SPECIAL_IDS` (Leiterbahn, Dotierung, and future one-shots — the Bruchmuster are NOT special, they fill the Würfel drawer), which keep their real category for packs/draft but are **excluded from their category drawer** — a third slot row there made the whole drawer row taller and squeezed the workshop (`_supply_drawer_rects` gives every drawer the max height). The vitrine stays **one column** as specials accumulate: `scene_root` reads only `size_for(…).x` and forces its height to the workshop's, so extra specials stack downwards into space that is already there, while a second column would widen it and eat the bench's width budget. One `CameraRig.Mode.WORKSHOP` zoom frames the whole corner, and everything in it shares **one** unit (`corner_unit` in `_setup_table_screen`), because a narrow drawer deriving `u` from its own width would render micro-type. Four rules govern the corner's size. `corner_unit` stays pinned to the **tray** width even though the bench is wider — hang it on the grown width and the drawers grow too, eating the gain. The bench's height is **not** bounded by the display rect but by the display's rounded edge: it reaches down to `TableScreen.glass_bottom_limit()` of the info bar's right end, and its width is capped by `glass_right_limit()` at the vitrine's lower edge — the workbench sits in the bottom-right curve, where a rect-based layout gets sliced diagonally by the glass. That makes the **hint bar the tallest lever in the corner**: it is the lowest element, so it deliberately stops above the *second* drawer — every pixel it is shorter buys glass depth, hence bench height. The bench's width is then derived from its height (`WORKSHOP_ASPECT` ≈ 2:1, floored at the drawer row's span), because that is the shape at which the station's 6×5 target grid sits flush beside the die column; flatter and the height-bound grid leaves a wide dead strip between the two. And `DieInspectorView`'s unit derives from **both** axes (`min(w/100, h/CONTENT_UNITS)`): width alone would let a wider bench magnify the station past its unchanged height. The corner has a **second zoom level** (`camera_rig.workshop_close`) reached only by **double-clicking empty workbench surface** — `scene_root._try_workshop_close_zoom` runs *before* the mouse forwarding (the window would swallow the event otherwise) and bails on any live button (`TableScreen.interactive_under`, the shared walker the hub's `interactive_at` also uses). The mode stays `WORKSHOP`, so click forwarding and the engraving ceremony carry over unchanged; right-click steps back to the wide view rather than out to the overview. Three rules make it work: the camera **stands still** there (no mouse look-around — the frame is brim-full, any pan would drag the trays in), reflections are off (like the title screen — the trays sit just outside the frame and mirror into it), and the view looks **straight down** (`WORKSHOP_CLOSE_TILT_DEGREES` = 0 vs. `ZOOM_BASIS`'s 15°) because from up close even a small angle skewed the workbench into a visible trapezoid. All view angles are one family — `tilted_basis(deg)` spans it, 0° = `TITLE_BASIS`, 15° = `ZOOM_BASIS`. The framing is solved, not tuned. The two axes are fitted **separately** (`WORKSHOP_CLOSE_MARGIN` for height, `WORKSHOP_CLOSE_SIDE_MARGIN` for width) because they land within ~1 % of each other, so a single `_fit_distance` flips between them; on a non-widescreen window the *width* binds and dictates the distance. Both margins are ≥ 1, so the corner always fits whole — the only question is where the leftover air goes, and that is the whole game: **above** the corner are the trays, **below** it is bare felt. So `_workshop_close_origin` seats the corner's **top edge** on the frame top and lets the slack pool underneath. `WORKSHOP_TOP_GAP` must stay ≥ 1.0: `tray_bounds` spans slot *centers*, so a smaller gap puts the bottom die row physically on the bench. And both `zoom_workshop_close`/`_wide` **emit `mode_changed`** although the mode is unchanged — the view changed, and without the signal every caller would have to remember to re-sync reflections itself. A **third level** (`camera_rig.die_focus`) belongs to the engraving station and is described there.
- **A die is never shown twice** — wherever the player decides *about a die* at the workbench, the die itself is on the bench: hovering in a `StasisEmitter` field like a tray die, at tray scale, bobbing on the tray's curve. `FloatingDie` (`dice/`) is that one object — real die + station + bob + the projection picking (`pick` → face / `PICK_FRAME` / `PICK_NONE`) + `spin`/`pose_to` — and it carries the `def` it shows so a caller can tell whether a standing stage already holds the right die. It is used by the engraving workpiece and by the pack ceremony; `scene_root` owns every instance (`engraving_stage`, `pack_stages`) because they are world objects, and `_stage_under` is the single "which die is the pointer on" answer that grabbing, the wheel and the hover card all ask. **Opening a dice pack therefore lays the choice on the bench**, and the unseal ceremony is where a die *becomes* a thing: the sign that bursts from the seal flies to the exact place its die will hover (`PackUnsealView.die_target_source`, asked at flight time because the window has no layout yet when the ceremony is built) and **turns into the body there** — it swells and fades while `FloatingDie.materialize()` grows the real die out of nothing at the same point. So a die never flies in and two dice never share a position. `WorkshopView` therefore lays the choice out **before** the seal breaks (`open_pack` sets the final phase right away) and hides only what would spoil it: per die a `_materialized` flag gates its net, while the net's *space* is reserved from the start — a net that appears and only then takes its room shifts the stage above it exactly as the sign is homing in on it. The old flat choice cards were `u*24 × u*30` each and ran out of the window's bottom edge — a window can hold three dice or three dossiers, not both. **The net under each die is the button**, not the die: clicking a die only brings it forward (`die_focus`) to be turned and looked at, and `choose_die` refuses a die that is not on the bench yet. Its cell is `DieInspectorView.TRAY_TILE` — the size at which a die is shown wherever one *decides about* it; the hover card's smaller `HOVER_CELL` is for mere information — and that width, not a guessed constant, is what spaces the three columns apart. The card in the window corner is therefore tray-only now; a pack die carries its net under itself. Its cells **explain themselves in the bench's info bar** (`net_hint_at`, asked per frame from `_update_workshop_hover` — the same bar the drawers and the engraving station speak in, so `_sync_workshop_net_hint` only ever takes back its OWN line). Asked, not reported: Godot swallows the first motion over a freshly hovered button as its enter event, so a pointer that comes to rest right there would never get a word. The choice also **replaces** the WERKSTATT title instead of adding lines of its own: the window belongs to the dice, and every line saved is net size. Since a pack always yields exactly one die, placement is **one die into one slot** (`_selected_slot`, not a list) and is built to read like the engraving station: die column left, pool grid right, and **no text in the window at all** — its guidance is `prompt()`, spoken in the bench's info bar like the station's. A hint label there is not merely redundant, it is destructive: without a wrap its minimum width drags the die column across half the window and leaves the grid a strip of stamps. Right-click there is a **step back in the flow, not in the camera** (`go_back`, checked in `scene_root` before the zoom steps): the unchosen dice were never destroyed (`_pack_dice`), they just stopped standing on the bench, so they come back and the chosen one walks over to rejoin them. The chosen die is **carried over, not respawned** (`_carry_over_pack_stages` + `FloatingDie.move_to`, which takes the station along): it is the same body, it only walks. A die still seeking a slot dies with the run (`_drop_placement` in the `run` setter), because it is a physical thing standing on the bench, not a page that can quietly stay open.
- **The workpiece IS the view** — the engraving station shows the die exactly once: as the REAL die, hovering over the station's stage. There is no flat projection beside it any more (`RotatableDieView` is gone; its selection color moved to `DieFaceDisplay.SELECT_NUMBER_COLOR`, its picking into `DieFaceDisplay` itself), and `DieInspectorView` therefore only holds the *procedure* — `scene_root` picks face and frame on the floating die and reports them in through `click_face`/`click_edges`/`set_die_hover`, while selection (`selection_changed`) and eligibility (`dimmed_faces`, grey numbers) travel back out onto it. It is a `FloatingDie` like the pack dice (gold field instead of their cyan) rather than resting on the bench — so the stage owns the whole column width: the emitter stands on the surface and the parallax puts it a little below and beside the die, and that footprint has to stay inside the stage instead of bleeding onto the target grid. Two consequences of the die being physical: hovering it drives the same engraving preview the net chips do, so the inspector keeps the two hover sources apart (`_hover_die` beats `_hover_chip`; merged into one field, the per-frame pick erased the chip the pointer had just entered) — and clicking it is grabbed in `scene_root._unhandled_input` **before** the mouse forwarding *and* before the workbench double-click, since the die floats over the window and is not free bench surface. A click on it opens the third bench level (`camera_rig.zoom_die_focus`, the die's half **space diagonal** so it fits in every rotation, camera standing still like the close view); there dragging turns it around the image axes and a click without travel picks the face under the pointer — nearest projected center wins, so the frame (= the whole-die tools' target) wins at the corner facing you. Right-click and wheel-down step back to the level the grab started from and lay the die back into its tray pose.
- **"Windows"** — each UI region (HUD/`HubView`, goal bar, dice pit) is a bordered panel with a shared `window_style()`. Outside the windows is dark-purple casino felt via `assets/shaders/table_felt.gdshader`. The combinations cluster is deliberately **not** a window: its chips stand on bare felt (see *Combo chips*), so `cluster_rect` survives only as geometry — zoom target, spill light, side-bet/slot-bank sizing, bus length — and is absent from the glass/felt `window_*` uniforms. Consequence: no glass there, hence no chip reflections.
- **The endless floor** — the felt doesn't end at the screen: `TableGround` (in `room.tscn`) lays a **3×3-tiled** plane just below Y = 0 with `assets/shaders/table_ground.gdshader`, which runs the *same* felt math as `table_felt.gdshader` over **virtual screen UVs** extrapolated from world coordinates (pattern stays in phase across the elliptical glass edge) and takes its visibility from an authored **emission pool** (`glass_energy` = the glass shader's 1.2, so the seam tone matches exactly) fading out past the screen rect — the scene lights (range ~55) can't carry a floor that size. Tiled because one huge plane would collect every spill light on a single mesh and blow `max_lights_per_object` (16); the center tile keeps the old table footprint, so its light load is unchanged. The Tisch-GLB is reduced to the elliptical `Screen` mesh: `scene_root.TABLE_HIDDEN_MESHES` hides rail, skirt, underglow, LED ring **and the chrome trim** (unlit chrome reads as a fat black ring in the dark room).
- **Light routing (core rule)** — every comet/meteor between screens rides the laid LED-strip network (`LedStripView` paths, chained via `_route_via_strips`); nothing flies free across the felt. The combo chips hang on that same network: `combo_wiring` is one `LedStripView` carrying the whole chip net in `rail_paths`, kept deliberately sparse: only the **shared** vertical buses (`combo_bus_xs` keeps an x only if it borders two columns — the outer ones served one side each and littered the felt), ONE cross rail along the cluster's bottom edge tying them together, and per chip a single stub per adjacent bus on the middle pin row. **Both external adern must land on a corner of that net, never on open track**: the hub ader enters at the bottom-right corner (right bus × cross rail, `link_hub_to_cluster` overrides the usual center entry for exactly this), and the score ader leaves at the top of the **left** bus (`link_score_strips`) and runs the cluster's top edge — which doubles as the upper cross connection, so the right bus needs no separate top rail. Light therefore crosses the net diagonally, hub corner to score corner. The Übertaktungs-Kauf rides it via `wiring_paths_to_cell`, which only ever uses buses that are actually laid, so edge columns get two comets and the middle four. When a route has to pass a window, the light travels **along that window's border** (`_border_route`), never through a foreign screen's interior — the slot-machine → stockpile route (`slot_engraving_route`) is the reference. The Schwarzmarkt hangs on the network as the slot bank's twin one storey lower: `secret_hub_strip` (`_link_secret_shop_to_hub`, laid by `place_secret_shop_window`) is the straight horizontal through the felt gap between the shop's right edge and the hub's left edge, and every ⚡ the back room costs — entry fee, purchase, reroll — rides it hub → shop against the laid direction (`secret_shop_pay_comet`, `CasinoStyle.CHARGE`), exactly like the slot stake. The round-end charm ceremony uses `_round_end_route`: charm pad → collector rail → score-window frame → pit data bus → around the pit half → hub (the bank comet's own path), then onward via the target strip (treasure strip for money, workshop + supply strip for engravings). Money made **inside a Zug** (gold faces, essence money, Streulicht, Lumpensammler) rides the same tail without the charm prefix — `take_money_comet` starts at the pit's data bus, one comet per take carrying the whole sum, and the booking already happened (`_suppress_money_light` keeps the generic hub→chest light out of its way, the arrival only glints). New travel animations must compose these helpers instead of drawing direct or free-form paths.
- **Reflections** — no SSR in `gl_compatibility`. `ScreenReflection` (`screen_reflection.gd`) is a `SubViewport` with a mirror camera (main camera mirrored across the plane, negated-X basis) rendering reflection-layer (`1<<10`) instances into a texture. `assets/shaders/screen_glass.gdshader` (`render_mode unshaded`, so scene lights don't paint the glass) blends UI + masked reflection; window rects/radii are pushed into its `window_*` uniforms by `TableScreen._sync_reflection_windows()`. `ScreenReflection.mark_reflective(root)` ORs the layer bit onto `VisualInstance3D`s.
- **Navigation is one set of discrete steps with three triggers** — mouse wheel up, left-click on a zone, and right-click/wheel down all drive the *same* `zoom_to`/`zoom_out`/`zoom_workshop_*` transitions. There is deliberately **no free or continuous zoom**: every distance is solved (texture resolution for the Schwarzmarkt, fitted rects for title and workshop-close), and everything downstream keys off the discrete `Mode` — `_screen_forwards_pixel`, reflections, the pit's route cards and supply tray — so a camera parked between modes has no defined answer for any of it. `scene_root._zone_mode_at` is the single target resolver both click and wheel ask (a locked window yields −1, its zone stands anyway); `_handle_zoom_wheel` sums `event.factor` so notched wheels step once per tick and trackpads accumulate, and is inert while the camera animates (that doubles as the flick guard), in the title HUD, and during the engraving ceremony — cancelling that is an intentional gesture, never an accidental nudge. On the workbench the wheel's next step is the close-up (`_workshop_close_zoom_allowed`, shared with the double-click), not a neighboring window — and over the engraving station's floating die it is that die (`die_focus`). During the ceremony the wheel therefore stays *on* the bench: it steps between the bench's levels but never out of the station.
- **`CameraRig`** (`camera_rig.gd`) — overview camera tilts to follow the mouse each frame. `set_tilt_locked(true)` freezes it (used while dragging the projected die); on release it holds for `TILT_RESUME_HOLD` (0.5 s) then `smoothstep`-eases the look-around back over `TILT_RESUME_EASE` (1.0 s) rather than snapping. `release_tilt_immediately()` cuts the resume short.

### Benchmark, Stresstest & Verträge mit dem Haus
The round goal is called **Benchmark** in all UI text (never "Blind"/"Ante" — deliberately un-Balatro). Every last round of a goal block (6, 12, …) is a **Stresstest** (`GameRun.is_stress_round`), and the settlement that ends it is the **Abrechnung**. Surviving it pays a prize: `GameRun.grant_stress_reward()` books ONE sealed 1-die pack with `essence_guaranteed` (`Pack.stress_die`) into `owned_packs`, right after `settle_block_deals` — the die itself is rolled only on opening, through the normal Werkstatt flow, so the unique/secret exclusions and the soul fallback come from the shared pack path. The ceremony is the hub-upgrade's: `scene_root._play_hub_reward_ceremony([pack])` reveals the seal over the hub and flies one `pack_delivery_comet` down the workshop ader. Booked first, flown afterwards, never awaited.

**Verträge mit dem Haus are the progression system.** From round 2 on the player signs one of three contracts (`GameRun.route_offers`) — the **first round of a run deliberately has none** (`advance_round` rolls the offers, `new_run` does not), so the player throws once before the house starts bargaining. A contract is **assembled from two clause pools**: one bonus + one malus `DealClause` of the **same tier**, never a fixed pair. **No deal outlives its round**: every clause is `Scope.INSTANT` or `Scope.ROUND`, so a contract is a bet on exactly one round — the question is whether *this* round can carry the malus, not how many rounds it will bite. `Scope.BLOCK` survives as the enum's third case and in `_scope_reaches`, but no clause carries it. `active_deals` entries still stay in the list **until the Abrechnung** even though their effect is long dead: the entry locks its clause against being offered again inside the block (`_taken_this_block`). `_scope_reaches` is the single arbiter of "is this clause live"; every effect query goes through `_clause_active`, never through raw membership (bonus vs. malus is a property of the clause, so ONE query suffices).

The benchmark curve (`goal_for_round`) starts at 150 and grows by `GOAL_INCREMENT` (75) per round, doubling the step every block: 150 … 525 (R6), 675 … 1425 (R12), 1725 … 3225 (R18). The **step is the only knob** — `BASE_GOAL` stays where it is, so round 1 is unchanged and the pressure builds.

The three cards are the three tiers, left to right and **always all three from round 2 on** — **Standardvertrag / Risikovertrag / Knebelvertrag** (the Knebel is no longer gated to block 2). `TREAT_CHANCE` (30 %) turns **one** slot into a **Werbegeschenk** (bonus only, no `CARD_MALUS`); which slot is weighted by `TREAT_TIER_WEIGHTS` (0.6 / 0.3 / 0.1), so the Standard slot usually gives the gift and the Knebel slot only rarely — `_roll_treat_slot` returns that index (−1 = none). Pairing is guarded four ways: bonus and malus of one card **share no tag** (otherwise the house sells zero-sum nonsense like "Auszahlung ×2 / Auszahlung ×0,5"), no clause lies out twice, no clause already signed this block, and never a second **benchmark-tagged** malus while one is active (a self-built unreachable goal is a death the player can't read — the guard is tag-based, so it covers the boss condition Hohe Erwartungen too). An exhausted pool falls back to repeats — an empty slot is worse. The Stresstest round swaps the whole offer for three of the six **Stresstest-Konditionen**: malus-only cards, so the choice is *how* you want to fight, not what you get for it.

Effects resolve **only** as `GameRun` queries dispatched on the clause id — never a silent branch in `scene_root`. `effective_goal()` inflates the stored `round_goal` (not `goal_for_round`, so a directly set goal still moves the bar) and `stage_size`/`cumulative_threshold` hang off it, which carries a benchmark clause into the bar, the overcharge stages and the win check at once. `effective_goal_for_round(n)` projects it onto the roadmap so signing visibly lifts **the station of the signing round** (no clause reaches further). Two traps the numbers impose: **money multipliers live in `add_money`** (`money_gain_factor`, positive deltas only — Happy Hour/Alles auf Rot are *all* income of the round, so they must NOT also sit in `round_payout_factor` or the payout double-dips), and `charge_split(stages)` takes **stages, not charges** (the Doppellader mints two per stage) while `add_charge(count)` takes charges — the shared `_split_charge` is what keeps them from drifting.

**Throttling** is no longer automatic in the Stresstest; it comes only from clauses. `hottest_combos(n)` picks deterministically at round start (level desc, tie → higher `HAND_PRIORITY`; `ONE_KIND` never, it's the fallback every hand must keep — and the tie must be broken *explicitly*, `sort_custom` is not stable) and only the Hitzewarnung uses it. The boss conditions Allrounder/Standardprotokoll make the list **grow mid-round**: `note_hand_taken(key)` is called from `scene_root._apply_hand_clauses` after every take and can lock even `ONE_KIND` — a throw with nothing scorable is then a farkle, by design. The list travels as `DiceScoring.CTX_THROTTLED` inside the same ctx every scoring call already gets, so preview, take and farkle comparison agree; `best_hand` falls through to the next matching category. The chip shows it itself (`ComboChipView.set_throttled` = red band + "AUS"). Because the boss condition is signed *before* the round, `apply_round_start_charms` sees it — that order is load-bearing.

**Parität (Schieflage/Gleichgewicht)** rides the same ctx (`DiceScoring.CTX_PARITY`) but bites **before** detection: `legal_indices` filters the dice, `qualifies`/`participating_indices` run on the filtered list and map the indices back, and the Vollzähler is intersected with the legal set. Consequences that must not be undone: `ONE_KIND` now qualifies only when a legal die exists (so an all-even throw under "nur ungerade" scores 0 and farkles), and `participating_indices` must keep returning REAL slots or materials and die-bound charms fire on the wrong die.

**Where it shows.** The choice lies **in the pit** (`RouteChoiceView`, a child of `TableScreen` spanning the pit's upper part above the net field — `scene_root._place_route_choice`); the card shows the **tier name** as its title (plus a decorative "§ N"), then the bonus clause (green) and the malus clause (red) — each is just its **effect text**, no clause name, no heading and no duration label (the card was too crowded; green/red carries the bonus/malus split, and the duration lives on the deal tokens as their size), tinted by `CasinoStyle.contract_tier_color`. Signing reports the **slot index**, not an id — a card is two clauses, so only its position identifies it. The round starts normally, and the cards appear the first time the player focuses the pit that round (`_on_camera_mode_changed`, same hook as the supply tray), i.e. right before the first throw. No close button, but **the pit may be left**: right-click and every zoom zone work as usual, the cards are pit furniture and go with the rest when the camera leaves (`_sync_screen_action_buttons` closes them), and the next pit focus lays them out again. Only the **throw** is gated (`route_pending`) — the player may look around the table before signing, but cannot start the round. Consequence of the re-entry: the decorative "§ N" is **derived from the clause ids** (`_section_for`), never rolled, or it would change every time the player comes back. The cards take the **whole pit floor**, so the pit's own furniture (action buttons, net field, material hint, both score orbs) hides while they show — driven from `_sync_screen_action_buttons`, which runs per frame and therefore also takes back what `update_pit_score`/`_refresh_ui` switch on in passing. The pit camera mode must forward clicks to the cards (`_screen_forwards_pixel`), which otherwise only passes the action buttons. Because the round now starts *before* the signature, the round-start effects are split out into `_apply_round_start_effects` and fire either immediately (round 1, no offers) or on signing — the boss condition must be known before the throttle is computed. The view's unit derives from **both** axes (`min(w/100, h/46)`); the pit is wide and flat, so width alone would produce giant type. Active sides live on as **tokens**, and the row is **mirrored**: one `DealTokenRow` under the hub's rim and a second along the pit's upper edge, both fed the same `GameRun.active_deal_sides()` from one place (`scene_root._refresh_deal_tokens`) so they can never disagree. Grammar (owned by `DealTokenRow`, not by either host): fill = the clause's **tag** color (same theme, same hue at a glance), ring green/red = bonus/malus, size = duration (the code still ranks BLOCK above ROUND, but with no BLOCK clause left every live token is the same size), glyph +/−; hover opens a `HintCard` — the shared card the Stresstest station uses too, which must be a child of its stage because it positions itself stage-relative. Rebuilt whole, never patched. **Every round end** sweeps both rows (`scene_root._sweep_deal_tokens` → `sweep_deal_tokens`/`sweep_pit_deal_tokens`, the longer awaited before the shop), because the clauses die with the round; the Abrechnung after a Stresstest then only clears the id locks (`settle_block_deals`) and must not sweep a second time.

Two rules the pit row lives by. It sits at the pit's top edge **left of center**, because the score window's data ader drops into the pit dead center — a token on that lane gets crossed by every scoring comet (`PIT_DEAL_RAIL_*`, world coords like the other pit furniture; its `u` comes from the strip height so the largest token fills it to 80 %). And its hover cannot use `mouse_entered`: the pointer is on the table, not in the `SubViewport`, and outside the forwarded rects no motion ever reaches the marks — so `scene_root._sync_pit_deal_hint` asks `pit_deal_token_at(pixel)` per frame (hence `self_hover = false` there), which also means the row comes and goes with the rest of the pit furniture in `_sync_screen_action_buttons`. Roadmap markers now only ever mark the Stresstest station, tinting the **bubble itself** — a dot under the disc was invisible from the overview distance, and marked stations deliberately ignore the distance fade (the Stresstest always sits farthest).

A new clause gets its id + factory + `all()` entry in `DealClause` (tier, scope, tags — the tags ARE the pairing rule, an untagged clause pairs with anything) and its effect as a `GameRun` query; a new *effect kind* also needs its call site (payout, goal, side bet, overcharge, shop price, per-hand, per-farkle) wired through the matching query. Clause-only, per-hand effects hang in `scene_root._apply_hand_clauses` — one place, so fees, grants and the growing throttle can never fire in different orders.

### Energie (⚡) & Schwarzmarkt
(The player-facing word for the resource is **Energie** — every UI text that names it in words says "Energie"; the ⚡ glyph stays as the compact symbol in numeric labels, and the code keeps `charge`/`add_charge`/`charge_cap`. "Überladung"/"Überladungs-Stufe" is a different word: the stage mechanic.)

**Every ⚡ the player GAINS travels to the capacitor bank as a comet** — there are exactly four sources and all four do it: the payout's cleared stages (`_play_bank_discharge`, which also books on arrival), the instant deal clauses (Startkapital & Co., `GameRun.instant_clause_charge` — the single source for both the booking and the ceremony), a won ⚡ side bet (`SideBet.Payout.CHARGE`, booked in `resolve_side_bets`) and the **Funkenflug**-Rift (`RiftEffects.charge_for_take`, collected in the `TakeReport` and booked in the take — once per Zug per face, never per activation). Clause, side-bet and Funkenflug charges are already booked when the ceremony starts, so `scene_root._play_deal_charge_volley`/`_play_side_bet_charge_volley`/`_play_rift_charge_volley` are **visual only** (`_fly_charge_to_capacitor(false)`) and must never book again — **book first, fly afterwards** is the pattern for every new source; both ride the same two legs as the payout (into the hub, then the hub-cluster ader to the bank), dense-staggered like the Frankiermaschine volley and guarded by comparing the run instance. Only leg 1 differs — the side bet leaves through its own window ader. Spending ⚡ (Discharge, shop entry, purchases, rerolls) is a loss and animates differently or not at all. `SlotPrize.Kind` has no charge kind — the slot machine pays only in goods.

Cleared overcharge stages pay **no money**: each mints one **Energie** into a capped wallet (`GameRun.charge`; `charge_cap()` = `charge_cap_rows() * CHARGE_ROW`, i.e. 5/10/15/20/25 at hub levels 1/3/5/7/10 — the cap only ever moves in **whole rows of 5** so a hub upgrade reads as "one row wakes up", never as a crooked number). Money comes **once** for the cleared benchmark (`MONEY_PER_ROUND_CLEAR`) — and again per stage that no longer fits. `charge_split(stages)` computes that split as a **pure preview**, planned *before any booking*; the booking itself happens stage by stage in `scene_root._play_bank_discharge`, one comet per stage on the existing bank route (cyan = ⚡ into the wallet, gold = overflow as money). **GameRun computes, the ceremony books** — never the other way round.

The **Schwarzmarkt** is **always on the table**, but barred: the window stands there from run start with a dark veil over three shadow slots and one big button in its middle that buys the way in for `GameRun.SECRET_UNLOCK_PRICE` (5 ⚡) — `unlock_secret_shop()` deducts the charge, rolls the first stock for free and emits `secret_shop_discovered`; it stays open for the rest of the run and a fresh run bars it again. Price and stock are both 5 ⚡, i.e. one full row of the base wallet: the barred shop is the first thing a player can spend charge on. The stock is only rolled **on unlock**, so while barred the view deliberately shows placeholders, never real goods. Stock is three fixed slots — legendary charm / special engraving from `Engraving.SPECIAL_IDS` / wildcard — priced in ⚡ and each buyable **once**; a sold slot stays empty. Charms already owned or already listed are excluded, specials already listed likewise (two identical slots at one price read as a bug), and an exhausted pool on either side falls back to repeats rather than an empty slot, so the stock can never go dead. `reroll_secret_stock()` swaps **all three** for `roundi(SECRET_REROLL_BASE * GOLDEN_RATIO^secret_rerolls)` ⚡ — a Fibonacci-like ladder 3 / 5 / 8 / 13 / 21, so the second reroll of a visit already hurts; the counter never resets within a run and `SecretShopView` reads the price per refresh (never caches it). The ⚡ wallet sits in the hub header from run start (deliberately unexplained before then). All charge visuals share one color, `CasinoStyle.CHARGE`; the Schwarzmarkt's own accent is the legendary violet.

**The shop is its own table window**, not a hub page: `SecretShopView` is a `Panel` that `TableScreen` owns like the slot bank, with its own `CameraRig.Mode.SECRET_SHOP` zoom, click zone and `_screen_forwards_pixel` case. There is exactly ONE way in — clicking the window — so it carries no close button (right-click zooms out, like every other window) and the hub footer has no entry. `scene_root._sync_secret_shop_state()` is the single idempotent writer (window **always** installed, click zone **always** armed — the unlock button lives inside the window, so a barred shop must still be zoomable —, `SecretShopView.set_locked(locked, can_afford)`, bank = charge/cap), so a fresh run resets everything *without* playing a ceremony; the unlock is just the transition (`_on_secret_shop_unlock_requested`: hub flash, then the entry fee travels the Schwarzmarkt ader as a ⚡ comet and only its arrival fires the `celebrate_secret_shop_install` shockwave — the same language as a newly installed slot machine; a run reset mid-flight is caught by comparing the run instance). Purchases and rerolls report their spent charge via `SecretShopView.charge_spent` so scene_root can send the same comet. Affordability is re-pushed on `charge_changed`, so the button greys itself. Its rect is **solved, not tuned** (`_secret_shop_rect`): right edge flush with the slot column, bottom flush with the hub — and the left edge walks rightwards until `glass_bottom_limit` actually carries that bottom, because the ellipse climbs steeply to the left (a full-width window under the slots would have ~60 px of glass at its left edge). The result is small and flat (~450×250 **texture** px, the smallest window on the table), and that number — not the visual impression — is what its zoom and its type are solved against. **A window is never magnified past its own texture resolution**: at the old `SECRET_SHOP_ZOOM_DISTANCE_CUT` of 11 its 451 texture px covered ~780 screen px, i.e. 0.58 texture px per screen px — a 1.7× upscale that read as "360p". The cut is 4, so 451 texture px land on ~440 screen px (~1.0). The lost apparent size comes back from the type instead: `CONTENT_UNITS` (54) sits just under the pocket's own aspect (~1.8) so the **width** binds, which is the largest unit the window can carry (`min(w/100, h/CONTENT_UNITS)` — and here "unit" *is* font size in texture pixels). Raising `TableScreen.SUPERSAMPLE` is not the answer: it multiplies the whole 1560×1060 viewport, measured 3 → 4 takes the frame from 35 to 58 ms and still only reaches 0.77 tex/px. For reference the slot bank sits at 1.28 tex/px — no window can beat it without a bigger rect. Adding it put the glass shader at exactly its 20-window cap, so `MAX_WINDOWS` is now 24 in all three window-masked shaders (`screen_glass`/`fumble_wave`/`table_felt`) — at the exact cap the *next* window silently loses its reflection.

`CapacitorBankView` is the physical ⚡ wallet — pure display, it never touches `GameRun`: a **fixed 5×5 grid**, all 25 cells present from run start, in three states — dark (row still locked), faintly **cyan** glimming (awake, empty) and a hot **amber** lamp, breathing on its own per-cell phase (an Energie stored). Amber is deliberately a different hue from `CasinoStyle.CHARGE` (the shared cyan) so a stored point can't be mistaken for the empty-but-awake glim, and its brightness is capped just over 1 in red: pushed higher it **clips to flat yellow and adjacent charged cells merge into one bar**, which destroys the countability the whole grid exists for. `_process` runs only while charge > 0. A cap change is therefore a **restyle, never a rebuild**: the upgrade moment is "a row wakes up". It stands **in the chip grid**, on the free slot at the cluster's bottom right (`TableScreen.free_cluster_slots()` derives the empty raster positions from the real cells, so a cluster rebuild carries it along), and **fills** it — but a single cell (~3.16:1) is a flat strip, so `scene_root` **stretches the slot ~2× downward into the bare felt below the cluster** (`CAPACITOR_SLOT_TALL`, top edge pinned to the chip row; the pit sits to the *right*, not below, and the glass runs far down there) to a ~1.58:1 target. The footprint's aspect is trimmed to just under *that* stretched slot (`max_width()/max_length()` ≈ 186/294) and `scene_root` fits the **tighter of both axes** (`CAPACITOR_SLOT_FILL` 0.97), so grid and slot agree on both axes at once (~97 %, lit cells ~94/90 %) instead of leaving the extra height as bare felt. Note `pixel_to_world` swaps the axes — slot **width** (pixel x) becomes world **z**, the grid's long axis. The cells are wide flat **bars**, not squares; the **row gap is the expensive number** — a row is only a few screen pixels tall, so too tight a seam melts the rows into solid bands. It sits on bare felt, where there is no glass, so it is deliberately **not** reflection-marked. It lies flat in XZ — the overview looks nearly straight down, and rows of 5 stay countable at the zoom distances. Emission only, no per-cell lights (the tiled ground has a 16-light budget). `pulse()` pops around the **resting** scale captured at pulse time — tweening to `Vector3.ONE` would permanently inflate the caller-scaled bank past its slot. The payout's ⚡ comet is therefore **two legs**: goal bar → hub (the existing bank route), then hub → capacitor along the **hub-cluster ader** (`charge_comet`), at whose entry corner the bank happens to stand. Leg 2 is deliberately *not* awaited — the next stage launches immediately, Frankiermaschine-volley style — and the booking (`add_charge(1)` + both pulses) happens on **leg-2 arrival**, guarded by `phase == Phase.PAYOUT`. Spending doesn't animate; the bank just resyncs from `charge_changed`.

### Extending content
A new **charm**, **engraving**, **essence** or **rift** needs no registration map: add a factory method + `all()` entry in the `data/` class and its effect in the matching `core/` effects class, both wired by the same id constant. Three charms died with the edge purge and must not come back by accident — **Rahmenvergolder** (it became a byte-for-byte duplicate of Goldschmied), **Magnetring** and **Zargenglanz** (no targets left). **Asset filename = content id** (`assets/models/<charm_id>.glb`, `assets/textures/engravings/<engraving_id>.jpg`); paths are derived by convention. `DieDefinition` is shared by reference — call `instantiate()` before mutating a die you take ownership of, or a later upgrade mutates every die sharing that definition.

**A pool entry is never swapped, only overwritten** (`DieDefinition.become`): the round deck, both trays, the workbench grid and the engraving station all hold the *same* instance as `owned_pool[i]`, so a purchase that replaced the instance left every one of them on the old die. `_replace_pool_entry` (dice purchase, slot-machine die) and `place_pack_die` therefore write **into** the entry — and every change to a pool die reports it through the single signal `GameRun.pool_changed`: the in-GameRun mutators emit it themselves, outside mutators (engraving station, `MaterialEffects.apply_take_effects`) call `note_pool_changed()`. `scene_root._on_pool_changed` is the one refresh path (three trays + `DiceController.refresh_faces` for the dice lying in the pit + the open station); never patch a single view after a mutation.

**Replacement vs. arrangement.** That rule governs *replacement* only. `GameRun.reorder_pool(from, to)` **swaps two array positions** — the instances travel to their new slots with their identity intact and their contents are never rewritten, which is exactly why instance-keyed state (Phosphoreszenz's base store, the Löschgas charge, both keyed by `get_instance_id()`) stays attached to the right die for free. `become` = a die's contents change; `reorder_pool` = a die's *place* changes. Pool order **is** the round deck's draw order, so arranging it before the round is strategy — nothing shuffles or normalizes it afterwards. Reordering rides the same window as engraving (`_dice_editing_locked()` false: pre-signature bench time and the shop), and reaches `reorder_pool` from two places — dragging a die onto another in the pool tray (`DiceTrayView.SLOT_PICK_LAYER`, the one hit path) and dragging tile onto tile in the workbench grid. `DiceGridView.reorder_enabled` is **off by default**: the shop's exchange picker is the same class in a different role and must stay a pure pick target.

### Hand choice & Farkle (fixed rule)
`DiceScoring.best_hand` walks `HAND_PRIORITY` top-down and takes the **first** category that qualifies and isn't throttled — there is **no score comparison across categories**. What physically lies on the table wins, however many points a lower-ranked chip would pay (three Zweierpäsche are never taken as a leveled-up Zwei Paare). Consequence: the throttle fall-through still works (a locked category is skipped, the hand slides one rank down).

The **Farkle rule is the same measure**: `is_strictly_better` compares only the `HAND_PRIORITY` **rank** of the two picked hands (`hand_rank`, smaller = higher) — **points never decide**. A reroll is safe iff it lands a strictly higher rank; the same rank farkles even with far more eyes (pair of 2s → pair of 6s), a lower rank farkles, and 3er-Pasch → 4er-Pasch can never farkle. Materials, edge materials and combo levels stay in the signature (they belong to the hand) but no longer influence the verdict; the **throttle in the ctx still does**, because it decides *which* category `best_hand` picks. A hand that scores nothing at all (parity/throttle) is never progress.

**The last dice are played out.** The round only ends automatically on a full overcharge, the hand cap, or an **empty** pool (`_round_should_end`) — a leftover of 1-5 dice is thrown as a smaller hand (the draw loop already stops at the pool's end). Consequences: `DiceController.set_slot_defs` pads the unused slots (every slot query runs over `count()`), detection runs over the **lying** dice only (`_auto_select_best_combo` goes through `_pit_combination_slots`, or the empty slots' zeros would form their own Pasch), and a hand that can neither be taken nor rerolled is a **Fumble**, not a dead end — `_on_farkle(false)` then skips the forgiving charms/clauses, which would only leave the hand unplayable. Leftover-dice payouts (Sparprämie & Co.) therefore only come from banking early; playing the rest out is the player's choice.

### Scoring trigger order (fixed — NO exceptions)
**Transform charms run first and are ONE ascending chain** (`CharmEffects.transform_value`): 1→6, 2→3, 3→4, 4→5, 5→6, 7/9→8. Ascending by design, so the chain keeps climbing — a 2 reaches the 6 with all four link charms owned — and every result (6 or 8) falls outside the trigger values, which keeps the chain idempotent. The Achterknoten is the only one coming from above (engraved faces climb past 6), and because detection uses `value % 10` it moves the Kombinationsziffer too — that IS the charm. The pit shows the effective value **on the die**: `DiceController.set_value_overrides` paints the up face's number in `DieFaceDisplay.PREVIEW_NUMBER_COLOR` (the same green as the workbench engraving preview — green means "not in the def" everywhere), driven from `scene_root._sync_transform_previews` on every `_refresh_ui`/`pool_changed` and silent during `Phase.SCORING`, where the running value owns the number instead. Display only: `values` stays what the scoring read. The **essence lens runs right after the chain** and shares the same seat — `DiceScoring.shown_value(raw, charms, essences)` is the one function that answers "what does this die show", and the preview calls it, not `transform_value`.

There are **two charm classes**, and the class decides *when* a charm fires:

- **Die-bound charms** (`CharmEffects.die_charm_*` hooks) hang on a concrete die and fire **with that die** in the die phase — Breitband/Straßenkehrer/Bodensatz/Prime Time per combination die, Leuchtturm/Hochstapler with the highest scored die (`die_charm_target_mult_at`), Beherit's crit with the lowest (`die_charm_crit_at`). When a die fires more than once (Argon & Co., Hasenpfote, Echo-Kammer, Nachglühen — `MaterialEffects.activation_count`), its die-bound charms fire **once per activation**, interleaved: Würfel → Charm-Anteil → Krit-Schlag, then the next activation. Within one activation: eyes → material (`MaterialEffects.*_once`) → die-bound additives → die-bound crits.
- **Static charms** (`charm_*_at` hooks) depend on the hand/state, not on a single die. They fire **after all dice, strictly in ownership (dock) order** — additive bonuses AND factors (Einserkult, Feierabendbier, Galgenhumor) apply at their exact position, never pooled at the end, so dock order is gameplay-relevant. **Static crits** multiply the *current* mult (`charm_crit_at`, `crit_x` on the charm step). After the base × mult merge, total-level effects (`charm_total_factor_at` — Zauberkarte) also run in dock order.

**Die-phase order is the lined-up row and is scoring-relevant.** The sweep iterates `DiceScoring.trigger_order(scored, dice)`: value-desc, tie → smallest slot — exactly the row `_line_up_settled_dice` lays out, computed canonically from the values so preview, scoring and the pit animation always agree (no `eye_order` parameter anymore). Because Beherit's ×-crit books inside the die phase, this order *changes totals* by design (mult added after the crit die's step escapes the ×) — that's why the order must stay canonical; never derive it from physical positions. `participating_indices` still returns slot-sorted indices; Echo-Kammer/Vorreiter target the min slot via `CharmEffects.first_participating`.

**The running value (Knochen/Glas between activations).** When a die fires more than once, bone growth and glass shrink happen **between** the countings — the second activation counts the grown (or shrunken) value. Inside the per-die loop `_base_and_mult` keeps a running value and mutates it after every activation via `MaterialEffects.mutate_value_once`, the **same helper** `apply_take_effects` writes into the defs, so the simulation and the permanent face can never drift (asserted by a test battery over bone/glass/glue/marrow/dotiert × 1-3 activations). Three boundaries are load-bearing: the mutation rides the **physical** value (`raw`, the untransformed faces — `score_category` keeps it, `best_hand` therefore passes RAW dice down and only detects on transformed ones), so a transform charm stays a lens and the run ends where the def ends; only **eyes and the die's own material math** follow the running value, while `trigger_order`, hand detection, `participating`/`scored` and every charm hook (`die_charm_*`, Beherit, Hochstapler) stay pinned to the settled values — a count must never reorder or retarget itself mid-play; and **Leiterbahn links keep their stored values**, a link being a different face. `ScoreBreakdown` mirrors it and gives each activation entry `value` (what it counted) and `value_after` (the physical value after the mutation), which is what `scene_root._play_die_pulse` switches the die's number to between pulses — in the NORMAL color, because the change is permanent, and the def carries the same number once `apply_take_effects` has run after the ceremony.

**Ties on a single-die charm (fixed rule).** When a charm means exactly *one* die picked by its face value (Hochstapler/Leuchtturm = highest, Beherit = lowest, Flickenteppich = highest), a tie is broken by **the first matching die — the smallest slot**. Never scan for the extreme value yourself; call `CharmEffects.target_die(values, candidates, highest)`, the single source of truth.

**Leiterbahn (pointers).** `DieDefinition.pointers` lets each face point at ONE adjacent face (`can_point`; opposite = `5 − i`, calibrated to `AXIS_FACE_INDEX`). After **all** activations of a die, the chain from its up face (`pointer_chain` — visited set, a cycle just stops) fires each link **once** as a full activation with the face swapped in: link eyes (transformed) → the link's face material (`MaterialEffects.*_once_for`) → die-bound charms **including ×crits**, all evaluating the link's value (`value_override`) while targeting stays by up values — still at the die's position in trigger order, and **never retriggered** (Argon & Co. multiply only activations). Links never join hand detection, and they never fire **rifts** — a rift belongs to the up face, a link is by definition another face. The chain is resolved **once** in `scene_root._score_ctx()` (`DiceScoring.CTX_POINTER_LINKS`, slot-keyed — remapped in `_score_ctx_for_slots`, snapshotted as `pre_reroll_links` into `is_strictly_better`'s `old_ctx` like the old materials; the walk length is **runtime state**, not def state — Plasma extends it via `pointer_chain(face, extra_links)`, and scoring ctx, take effects and preview must all call it with the SAME extra); take effects resolve it themselves from the defs (Gold pays once per link, Knochen/Glas hit the **link** face, never × `effect_count`). Applied in the Werkstatt: the EPIC dice-category engraving **"Leiterbahn"** (a Sonderposten: `material_id()` returns `""` for every `is_special_id`, and the Gravierstift spares none of them; stored in the Sonderbestand vitrine, not the Würfel drawer — see *The workbench corner*) uses the Meißel-style two-step pick with the second pick adjacent-only; overwrite allowed. `DieNetView` draws each pointer as an arrow on the source cell's border matching the crossed cube edge (`POINTER_SIDES` — adjacent faces aren't always adjacent net cells, so no connecting lines), and during counting the link pulses reuse `_play_die_pulse` while the pit net re-shows the die with the link face gold-framed.

**Sättigung (Materialstufen I–III).** `DieDefinition.levels` holds, per face, the level of the material *sitting on that face* (0 = none, else 1–3). The level belongs to the material **instance**: `set_face_material` is the single write path for `materials[face]` precisely so that overpainting always resets it to I (Schmuckkästchen, Midashandschuh, the material engraving and both die factories all go through it) — but it never touches the face's **rift**: Stufen wohnen in der Glasur, Rifts in der Struktur der Schale. Levels are climbed two ways, and **the climb is priced in duplicates**: the **same material engraving again on the same face** (`raise_level`) costs the **target level** in copies — I→II two, II→III three, fresh paint one, so bare to III is 1+2+3 = **6 of one type** (`GameRun.consume_engravings`, all-or-nothing with a single emit). A face whose raise the stock can't cover is simply **not eligible** — it dims like any other non-target, and the hint bar must say *why* (`_short_stock_face`), because a dimmed cell alone never explains itself. The other way is the EPIC Sonderposten **"Dotierung"**, whose wildcard power is that it lifts a material face **straight to III** from wherever it stands (eligibility is still "material face below III", hence its own "no legal target" prompt) — that jump is what makes it epic. The cap is `DieMaterial.MAX_LEVEL`. Each material's II and III are hand-set — sometimes scaling, sometimes transformation: Bernstein +20 / +50 flat **plus the eye sum on every level**, on III only 5 × eye sum; Gold +$3 / +$7, on III additionally +$1 per gold-**face** trigger of that take (counted in one pre-pass before the first booking); Knochen grows +1 / max(3, 10 %) / max(3, 20 %), **compounding per activation**; Rubin +4 / +10 Mult and on III a **crit ×2**; Glas +eyes, on II a **crit ×eyes** instead, on III **both** — and it eats itself at the II pace. Rubin III and Glas II/III are the reason the whole thing is order-sensitive: a material crit fires inside the die phase, in the crit sub-step **before** the essence crit and the die-bound charm crits (Beherit), in both the activation and the link block — so `MaterialEffects.mult_bonus` can no longer express a full result and survives as an additive preview helper only, with `DiceScoring._base_and_mult` authoritative. Charms that raise a base number keep their **surplus above it** (Bernsteinzimmer +30 on every level, Knochenleim over the step, Goldschmied/Goldader over the level's rate — Knochenmark doesn't touch the step, it adds a **trigger**: every bone firing happens `1 + copies` times, and the percentage step recomputes per trigger, so two triggers on 40 give +4 then +4.4→5, never 2 × +4) — never a factor on the raised value, or the level would multiply with its own support charms. The per-die facts the effects need (up-face level, eye sum) ride in `ctx` like the Leiterbahn chains (`DiceScoring.CTX_MATERIAL_LEVELS`, slot-keyed — **remapped** in `_score_ctx_for_slots` and snapshotted as `pre_reroll_levels`, or preview and farkle comparison silently judge the wrong dice); take effects read the defs directly. `DieNetView.level_badges` marks a raised cell in its bottom-right corner — free, because pointer arrows sit at the edge midpoints — as geometry, not type: at the 30-die grid's ~17 px cell a glyph is mush, so the dark plate carries one bar per level and the "II"/"III" resolves only from ~30 px up; level I stays unmarked, it is the normal case. The station composes its own cells, so it adds the badges itself.

**Essenzen (die Seele des Würfels).** `DieDefinition.essence_id` is **innate**: sealed into the shell at casting, with no application path anywhere — only die factories and offers write it (`DiceOffer.roll_essence`, shared by shop, packs and the slot-machine die prize). `Essence` (data) carries name, epithet, rarity, `glow`, `secret` (Schwarzmarkt-only) and `unique` (Legendäre); `EssenceEffects` (core) resolves the behaviour by id. **Kanten-Materialien are gone entirely** — the edges are no longer an upgrade slot, only the stage the essence glows on (`DieFaceDisplay` tints the frame by `Essence.glow_for`, essence-less dice keep the neutral neon). Consequences that must hold: **the essence is the ONLY multiplicative source per die** (`activation_factor` — Argon 2, Quecksilberdampf 3, Elmsfeuer 2/4 im Stresstest, and the Quecksilberdampf **charm** adds +1 to any factor ≥ 2); everything else that grants activations is **additive** (Retrigger-Charms, Echo-Kammer, Sauerstoff, Sonnenwind, Nachglühen), so `Faktor × Faktor` can never explode again. `secret` essences never appear in the normal shop or in packs, `unique` ones are excluded once owned and never roll onto a bundle > 1, and a purchase replaces a **soulless** pool slot first (`GameRun._replace_pool_entry`) because a soul is not re-obtainable. The essences ride the ctx as `DiceScoring.CTX_ESSENCES` (slot → id), `CTX_ESSENCE_SET`, `CTX_RIFTS`, `CTX_PHOSPHOR_STORE` (slot → stored base points, round state only `GameRun` knows) plus the hand-wide `CTX_STRESS` and `CTX_TURN_INDEX` (the round's Zug number, 1-based — Lawinenlicht grows by it); every slot-keyed one is remapped in `_score_ctx_for_slots` and snapshotted as `pre_reroll_*`. **No essence touches the trigger order** — `trigger_order(scored, dice, declared)` knows only the canonical value-desc/slot-asc rule and the player's declared arrangement.

Three shapes an essence effect can take, and each has exactly one seat: a **lens on the shown value** (Wasserstoff ×2) sits in `DiceScoring.shown_values`/`shown_value`, right after the charm transform chain — so detection, targeting and the pit preview all see the doubled number while `raw` (the physical faces, and with them the value mutation and `score_category`) stays untouched; **link faces** (Röntgenlicht's opposite, Korona's four neighbours) come from the single `EssenceEffects.link_faces`, which the scoring ctx, the take effects and the gold-trigger pre-pass all call, chain first and every face at most once; and **permanent face growth** (Helium, Strahlungsdruck, Lawinenlicht) rides `MaterialEffects.mutate_value_once` for the up face while the take writes the remaining five, so simulation and def can never drift.

**Krits are floats.** `EssenceEffects.crit_once_for`/`crit_of`, `MaterialEffects.mult_crit_once_for` and both `CharmEffects` crit hooks return `float`, and the mult side of `DiceScoring._base_and_mult` is a float all the way down. There is **exactly one rounding in the whole formula** — `ceili(base × mult)` at the merge — so two Xenon crits are ×2.25, never twice-rounded ×2. The crit *count* (Ozon's ramp, Grubengas's per-crit bonus) therefore compares with `is_equal_approx(crit, 1.0)`, never `!= 1`. Every printed mult goes through the one format rule `ScoreBreakdown.format_mult`/`format_number` ("×2", "×1.5", "×2.25"); the combo chips keep printing their integer level mult.

**Rifts (Kernlicht).** A rift is a controlled fracture of the shell, sealed with tinted glaze — the tint IS the effect. `DieDefinition.rifts` holds one per face; `second_rifts` is a parallel array that **only Vakuum dice** may write (`rift_slots()`), because without inner pressure the shell carries a second break, and the Vakuum's cracks render **black** whatever the type. Four kinds in three classes: **Nachglühen** (Wertung) adds +1 activation, additive like every non-essence source; **Funkenflug** (Wertung) mints +1 ⚡ once per Zug — the fourth charge source, booked in the take and flown afterwards; **Streulicht** (Ökonomie) pays +$1 for every die that lies **unscored** at the end of the Zug showing its cracked face (the deliberate counter-event to Gold, hence `apply_take_effects` takes the `lying` slots); **Einbrand** (Schutz) burns the face value in — it cannot shrink (glass, Radon decay both skip it) and its material cannot be overpainted, while saturating the SAME material, value engravings and re-breaking stay allowed. Rifts belong to the **up face**, so Leiterbahn links never fire them. They travel as `DiceScoring.CTX_RIFTS` (slot → id list), remapped and snapshotted as `pre_reroll_rifts` — the Nachglühen changes activation counts, so the farkle comparison needs the old breaks. Acquisition is the **Bruchmuster**, four Würfel-category engravings (`Engraving.BREAK_PREFIX` + rift id) that refilled the drawer the edge purge emptied; the station's pick is one face, an occupied slot is replaced. The crack geometry has ONE source (`Rift.crack_lines`, normalized polylines) feeding both the net view and the generated 3D overlay texture, so table and workbench can never show different patterns. Timing separates the two light systems: the essence glows **constantly**, a rift only shimmers at rest and **flares in the moment it fires** (`DieFaceDisplay.flare_rifts`, driven from `_flash_scoring_die`). No per-rift lights — the tiled ground's 16-light budget forbids it, so emission carries alone.

`ScoreBreakdown.build` mirrors the formula 1:1: every die step carries per-activation entries (`activations`: die pulse → `charm_*_add/after` → `crit_x`/`mult_after_crit`), played by `scene_root._play_die_step`; static charm steps stay in the charm phase (`_play_crit_step` for static crits). When adding a charm, put it in the class where it belongs — a die-bound effect in the `die_charm_*` hooks, a static one in the `charm_*` hooks — or the animation fires it in the wrong phase.

The same rule holds at **round end**: after the round payout and before the shop opens, round-end charms fire strictly left to right in `scene_root._play_round_end_charm_ceremony`, and every effect is **visible** — money charms (Zinsgroschen, Überflieger — $5 per **cleared overcharge stage**, i.e. the visible bar, so the Doppellader's second ⚡ per stage changes nothing —, Glücksgroschen, Notgroschen) pay as **real chip denominations** (`ChipStackView.split_gain`, each packet in its chip color) launched in a dense stagger from the dock pad, every packet booking its own value on arrival; Frankiermaschine fires one meteor per engraving as a dense volley (`STAMP_METEOR_GAP` between launches, no waiting for the previous arrival), each granting on its own arrival (`GameRun.roll_stamp_engraving` rolls, the ceremony grants). All of it travels the LED-strip route through score window, pit and hub (see *Light routing*). A new round-end charm gets its case in that ceremony — never a silent mutation in `GameRun`.

## Testing notes (GUT quirks)

- **`test/unit/`** — fast pure-logic tests (no scene tree). **`test/integration/`** — tests that build nodes.
- GDScript won't auto-convert untyped array literals to the typed `Array[int]`/`Array[String]` these APIs expect — use the `_d()`/`_ids()` helpers (they `.assign()` into typed arrays). Pulling from an untyped `Dictionary` needs an explicit type (`var k: String = h["key"]`, not `:=`).
- `assert_signal_emitted_with_parameters` chokes on **bool** params (crashes in `signal_watcher.gd`/`diff_tool.gd`) — record emitted values manually via a `connect` lambda and assert the resulting array instead.
- `get_global_rect()` on freshly-built container children returns a zero rect until a frame passes — `await wait_frames(2)` before asserting layout.
- For inspector/engraving tests that apply etchings: `view.run = GameRun.new_run()` then `view.run.grant_engraving(Engraving.chisel())`.
