# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Fumble** — a Balatro-like 3D dice roguelike built in **Godot 4.7** (`gl_compatibility` renderer, Jolt physics). Code comments and in-game text are in **German**; identifiers are a mix. The whole game plays on a single table surface at world **Y = 0**, viewed as a "casino table screen": 2D UI is rendered into a `SubViewport` and displayed on a mesh (see Architecture). The table has **no edge**: the felt runs on as an endless floor that fades into the dark room (`TableGround`), leaving space for future features around the play area.

**Comments:** keep them to the necessary minimum — short German one-liners that state a non-obvious rule, constraint, or design decision. Don't restate what the code already says, don't duplicate a `description` string that sits one line below, and don't write essay-length narrative blocks or "siehe X" cross-reference chains. When in doubt, cut it.

## Architecture

### Layered `scripts/` — the folder IS the dependency rule
`core/` and `data/` must not import from folders below them. New scripts are placed by layer, not by feature:

- **`data/`** — reine `Resource`-Records (inkl. `DealClause`); jede Id als `const`-String (single source of truth). Details: `scripts/data/CLAUDE.md`.
- **`core/`** — pure Logik, **keine Nodes** (`RefCounted`/static): Scoring, Effekt-Auflösung, `GameRun`, Verträge, Energie-Ökonomie. Details: `scripts/core/CLAUDE.md`.
- **`dice/`** — der physische Würfel: Physik, Builder, Face-Display, Schwebe-Stationen. Details: `scripts/dice/CLAUDE.md`.
- **`table/`** — 3D-Requisiten, Kamera und das Tisch-Display samt Bühnenmaschinerie (Vitrine, Hebebühne, Data-Cells, Licht-Routing). Details: `scripts/table/CLAUDE.md`.
- **`ui/`** — 2D-Fenster und Styling im Tisch-Display: Laden, Werkstatt/Presse, Magazin, Wetten. Details: `scripts/ui/CLAUDE.md`.

Die ausführliche Architektur-Doku liegt in diesen verzeichnis-lokalen CLAUDE.md-Dateien; Claude Code lädt sie, sobald dort Dateien angefasst werden. Wer ein Subsystem anfasst, liest die CLAUDE.md seines Ordners zuerst — Querverweise („siehe *X*") können in einer Schwesterdatei liegen.

### `scene_root.gd` — the single coordinator
Top-level `Node3D` (not in a subfolder). Owns exactly one `GameRun`, wires its signals to the UI, drives round flow (throw → score → take/reroll → round-goal → **Auszahlungs-Seite mit Kassieren-Halt** (der Hub wird zur Cash-Out-Seite und die Runde steht, bis „Kassieren" gedrückt ist — siehe *Die AUSZAHLUNGS-SEITE* in `scripts/ui/CLAUDE.md`) → shop — and the **pit is the shop's second exit**: focusing it while `phase == SHOP` means "Fertig", so `_on_camera_mode_changed` calls `ShopController.close()` and `_on_shop_closed` only zooms back to the overview when the camera really stands in the hub, never yanking back a flight already under way), and passes the same `GameRun` instance (typed) to `ShopController` and `WorkshopView`, which mutate state **only** through `GameRun` methods. It also does mouse-forwarding: `_forward_screen_mouse` projects window clicks onto the table plane and `push_input`s them into the `SubViewport` (the projection is camera-independent and runs in every pose, the free camera included); `_screen_forwards_pixel` asks which VISIBLE window owns the pixel — see *Sichtbar heißt bedienbar*. `_ready` is split into named setup steps (`_setup_dice`/`_setup_table_screen`/`_setup_camera_targets`/`_setup_panels`/`_setup_settings_ui`); camera raycasts go through the shared `_ray_pick(pos, mask)` helper and click zones through `_add_click_zone`.

Eine Data-Card steht in `PackDrawerView.CASSETTE_SCALE` (2,184) — im Magazin, in der Schacht-Reihe, in der Laden-Vitrine, im Schwarzmarkt, als Wett-Gewinn, als geworfener Einsatz und auf der Auszahlungs-Ablage —, ein Würfel in `DiceTrayView.DIE_SCALE` (0,6). **Der ROLL folgt der LAGE** (Welle O, 2026-09-04): sie LIEGT quer in jeder Verkaufs-Auslage, in der Wette und im Wurf (um die Blickachse gerollt, Langseite waagerecht), und sie STEHT aufrecht im MAGAZIN und im Serien-KERF. **STEHEND ist sie seit der Welle P HOCHKANT** (`DataCellView.STAND_YAW`, eine Vierteldrehung um die Hochachse, die wie der Roll der LAGE folgt): ihre Fläche zeigt nach Bild-LINKS, von oben ist sie ein SCHMALER, TIEFER Balken (gemessen 35,9 × 88,5 px statt 88,5 × 35,9), und Magazin wie Schacht-Reihe stehen damit Fläche an Fläche wie eine KARTEI. Die ×n-Marke schaut MIT der Fläche (Welle R) — sie ist ein Kind des Körpers und dreht mit ihm. LIEGEND ändert sich nichts. Die EINE, hochkante Netz-Backung bleibt und füllt sie ohne Rand — auf der stehenden Karte liest sie darum um eine Vierteldrehung gekippt, und dafür gibt es das SUMMEN-NETZ im Streifen. `DataCellView.STAND_HEIGHT` (= `HEIGHT`) ist ihr aufrechtes Maß, an dem JEDE senkrechte Rechnung mißt — Einsinken, Aufstieg, Griff-Hub und die Tiefe jeder Grube; das ortsabhängige `stand_measure` ist tot. Wer eine Fassung baut, paßt SIE der Größe an — die Schacht-Reihe rechnet ihre Münder aus Kartengröße plus Fuge und läßt notfalls den ganzen Werkstatt-Streifen nach rechts wachsen, nie umgekehrt. **Die Karte ist aus GETÖNTEM GLAS, sie steckt nur zu EINEM VIERTEL, und der GRIFF zieht sie zu dreien heraus** (Spieler-Entscheide 2026-09-04, Welle Q): Gehäuse und Kern sind alphagemischt in der Sortenfarbe (`GLASS_BODY_ALPHA` 0,32, `CORE_ALPHA` 0,45), das Netz-Quad beidseitig — von HINTEN liest dieselbe eine Backung durch den Körper hindurch, gespiegelt, und Kopfkante, Blende, Kragen, Finnen und Siegelband bleiben MASSIV; `SUNK_SHOW` steht auf 0,75 (drei Viertel stehen über dem Blech), `PIT_HOVER_LIFT` auf 0,78 (drei Viertel über der Grubenkante). **Die KAPPE ist am 2026-09-04 gestorben (Welle R): die SORTE sagt die FARBE, die GRÖSSE ihre INTENSITÄT** — `tier_tint()` entsättigt die Sortenfarbe stufenweise zum Grau GLEICHER Helligkeit (`TIER_SATURATION` 0,55 / 0,8 / 1,0), `tier_energy()` dämpft jede Emission (`TIER_ENERGY` 0,70 / 0,85 / 1,0 — der Faktor dämpft nur, denn die authored Energien stehen schon an der Bloom-Schwelle 0,95); beide lesen JEDE getönte Fläche (Glas-Körper, Kern, Kopfkanten-Saum, Rahmen, Netz-Backung). Die Rahmenstärke (`TIER_LIP_GAIN`) bleibt der stille zweite Kanal; Sortenzeichen, Größen-Streifen, goldener Kolossal-Kragen und der Glyphen-Ofen sind mit der Kappe gestorben, `CAP_DEPTH` überlebt als reines Griffmaß `GRIP_DEPTH` (dieselbe Zahl — Teilung von Reihe und Magazin bleiben byteweise gleich), und die ×n-Marke liegt in JEDER Lage auf der KARTENFLÄCHE (freie obere Ecke des Netz-Kreuzes). - **Der VORRAT hat ZWEI ANSICHTEN, und der RASTER-UMSCHALTER legt um** (2026-09-03): KÖRPER (die schwebenden Würfel) oder RASTER (die GLAS-ANSICHT — der Vorrat versinkt, der Gruben-Schirm fährt zu und trägt die Anzeige, und darauf liegt das Netz-Raster des Vorrats, Sitz i = Zelle i). Der Umschalter ist eine flache Taste auf dem freien Filz ÜBER der Grube (`RasterSwitchView`, bündig mit deren Bildschirm-rechtem Ende — die eine Kante, an der neben dem Loch noch Platz ist, und sie steht an Pool- wie Werkstatt-Station im Bild); ihre Aufschrift nennt, was der Druck LIEFERT („RASTER" / „KÖRPER"), und blind bleibt sie STEHEN und wird nur grau. **Der ZELL-TIPP bedeutet zweierlei, und der Neuzugang entscheidet**: wartet einer im Ausgabefach, ist die Zelle sein Tausch-Ziel (`exchange_pending_die`, gebucht sofort), wartet keiner, wählt sie wie der Tipp auf den Pool-Körper das ZIEL der Serie (`WorkshopView.set_target_die`; die Bühnen-Fahrt aufs Podest wartet auf den stehenden Vorrat, holt ihn also beim Schließen) — und die gewählte Zelle trägt den Gold-Saum. Zug legt um, Rechtsklick schließt, das ZURREN schließt HART (das Raster darf nur stehen, solange der Vorrat stehen dürfte). **ZWEI Wege hinein, EIN Weg hinaus** (`_close_deck_glass`, hart `_settle_deck_glass_hard`): der UMSCHALTER öffnet den DAUER-Modus (`_deck_glass_pinned`) — er rahmt NICHT um, merkt sich keine Station und überlebt darum den Stationswechsel; der TIPP auf einen Neuzugang öffnet die enge Tausch-Frage, die ENG heranfährt (Rahmen = Pool-Loch ∪ Neuzugangs-Säule, ~85 % Bildfüllung, TEMPORÄRER Rahmen ohne Moduswechsel), an die gemerkte Station zurückkehrt und beim Wegzoomen abbricht. **Liegen mehrere Neuzugänge, bleibt sie nach einer Wahl STEHEN** (die SERIE, 2026-09-01): der nächste rückt ins Fach nach, Kopfzeile und Info-Säule wechseln auf ihn — und weil `exchange_pending_die` die Indizes verrutschen läßt, ist der offene Neuzugang IMMER Index 0. Das Raster prüft seine Frische am INHALT (`DeckGlassView.pool_signature`), nicht an den Referenzen: der Tausch schreibt per `become` in die Instanz, die Liste bleibt gleich. Die Pool-Maschine kennt für das Raster eine ZWEITE Park-Konfiguration (tief, mit Schirm); die der RUNDE (flach, schirmlos) bleibt unberührt. Das Raster wohnt seit 2026-08-31 in einem EIGENEN, nicht-HDR-SubViewport mit `transparent_bg`: nur so trägt es echtes Per-Pixel-Alpha (der Helligkeits-Key und die Filz-Schwärzung sind damit gestorben), und seine Auflösung wird an der GEMESSENEN Bildschirm-Pixeldichte des Schirms bemessen statt am fernen Ausschnitt der einen Anzeige — gemessen 1,35 Texel/Pixel an der Pool-Station und 1,64 an der Werkstatt-Weitsicht (dort ist das Raster nur KLEINER: Netz-Zelle ~7,8 Bildschirm-px gegen ~11,7 am Pool, gemessen bei 1280 × 720). Rechtsklick wählt ab; ein Kamerawechsel NICHT (das Podest gehört dem Fenster, nicht der Station). Die SCHABLONE kehrt am Ende ihrer Fahrt DORTHIN zurück, wo sie geboren wurde, und faltet sich in den stehenden Würfel — kein Seitenwechsel mehr. - **Der DOPPELKLICK auf den Podest-Würfel öffnet die INSPEKTION** (2026-09-01, an der Straße seit 2026-09-03 die einzige Nah-Geste): die Kamera fährt SUPER NAH heran — Rahmen = halbe Raumdiagonale mal `CameraRig.DIE_FOCUS_MARGIN`, gemessen ~7× näher als die Station —, der Würfel legt sich in die Dreiviertel-Ansicht (`die_focus_basis`, drei Seiten auf einmal), die Kamera steht STILL, und ein ZUG dreht IHN um die Bild-Achsen (`FloatingDie.spin`; ohne Fokus dreht derselbe Zug ihn an Ort). Sie ist **MODAL wie die Glas-Ansicht**: im Bild steht nur der Würfel, `_screen_forwards_pixel` schweigt, und WASD wie Doppelklick-Nahsicht sind taub. Wie die Glas-Ansicht ist es ein **TEMPORÄRER Rahmen**: `zoom_die_focus` meldet keinen Wechsel und rührt den Modus nicht an; die Lage davor merkt sich `scene_root._die_focus_home`. - **Das Bewegungs-Gesetz liest sich nach URHEBER**: was der *Spieler zahlt*, fliegt als KÖRPER im ballistischen Bogen (der WURF, `scene_root`s `#region Der WURF`); was der *Tisch liefert*, reist als LICHT über die gelegten Adern (die AUSNAHME seit der Korrektur-Welle I: Kassetten-Lieferungen ANS MAGAZIN fliegen als reiner METEOR-BOGEN ohne Ader, denn die Hub→Magazin-Ader ist gefallen; die Quell-Adern von Automat und Schwarzmarkt leben weiter); was er *präsentiert oder einzieht*, fährt per HEBEBÜHNE durch die Fläche. Unter dem Tisch bleiben die Lieferung ins Magazin, das Absinken der verbrauchten Karten nach dem Griff und die Fahrten, die der TISCH führt (Auslagen, Schluck, Wett-Tresen). Umgesetzt ist der Wurf bisher für den Nebenwetten-EINSATZ — Laden und Werkstatt zahlen noch Licht, ihr Umzug ist eine spätere Welle. Das Fenster malt nur Münder, Netze und den leeren Podest-Platz und MELDET ihre Anker (`press_slot_anchors`/`press_display_anchors`, `target_net_center`/`target_projector_y`, `ist_net_center` als Geburts- UND Landeplatz der Schablone), die Körper gehören `scene_root`. **Die HÖHE ist LINEAR gelöst** (Welle S): zwei Posten sind WELTMASSE und hängen nicht an u — die Kerf-Höhe (96,41 px) und die Netz-Höhe (125,28 px) —, also `u = (Pool-Höhe − Kerf − Netz) / (height_units() + apron_span_units())`; gemessen **u = 3,357 px**, Fenster 537,3 × 261,6 px, `bench_rect` 537,3 × 402,5. `scene_root._fit_workshop_rect` legt den Streifen an: linke Kante bündig mit der POOL-REIHE, Oberkante eine Naht (`_pool_seam_px`) unter ihr. Die BREITE zählt jetzt EINE Spalte und EINE Fuge (`bench_width_for(slots, u, card_px, net_px)` — die Spaltenbreite gibt das NETZ vor, `DIFF_WIDTH_UNITS` ist nur ihr Boden). Die Kamera (`configure_workshop_target`) rahmt allein Streifen und Magazin, OHNE Pool und OHNE Ausgabefach. Siehe *Die STATIONS-ZEILE* in `scripts/ui/CLAUDE.md`.
- **UI-Wort vs. Code-Wort**: Energie/`charge`, Gravur/`Engraving`, Veredelung/`dope`, Pointer (die LED-Adern behalten „Leiterbahn"), Benchmark (nie „Blind"/„Ante").
- **Sichtbar heißt bedienbar**: was bedient werden darf, hängt an Sichtbarkeit, nie an der Kamera-Station. Es gibt genau ZWEI benannte Ausnahmen: der Setzen-Klick des Wett-Tresens (2026-08-26) — gewettet wird nur an der eigenen Station, aus der Ferne wird der Klick zum Zoom — und der Schwarzmarkt-KAUF (2026-08-30): gekauft wird nur an der eigenen Station, aus der Ferne wird der Klick zum Zoom; Hover, Schilder und Tooltip antworten überall, wo die Ware steht. Neue Ausnahmen werden hier benannt oder es gibt sie nicht.

## Arbeitsweise (Spieler-Entscheidung 2026-08-25)
- **Delegiert wird nur bei echten FEATURE-WELLEN** (neue Mechanik, mehrere Subsysteme, Umbau einer Grammatik) — dann Plan-Datei + Opus-5-Subagent wie gehabt. **Kleine Änderungen macht die Session SELBST**: Ein-/Zwei-Datei-Fixes, Konstanten, Farben/Maße, visuelle Tweaks, Bugs mit bekannter Wurzel. Kein Plan-Dokument, kein Agenten-Aufsatz für so etwas.
- **Getestet wird EINMAL AM ENDE**, nicht nach jedem Schritt: ein Suiten-Pass, wenn die Änderung steht (plus Boot, falls `scene_root.gd` angefasst wurde). Kein Wiederholen der Läufe, die ein Subagent gerade grün gefahren hat — sein Log prüfen genügt (immer mit dem `Ignoring|Parse Error`-Grep, siehe unten); der eigene Vollpass gehört vor den Commit.
- **Beweis-Aufwand nach Anlass**: Kennfarben-Aufnahmen, Pixel-A/B und Frame-Serien gehören zur Artefakt-Jagd (dort haben sie dreimal die echte Ursache statt einer Vermutung geliefert) — nicht zu Geschmacks-Änderungen.
