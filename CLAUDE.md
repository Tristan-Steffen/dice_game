# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Fumble** — a Balatro-like 3D dice roguelike built in **Godot 4.7** (`gl_compatibility` renderer, Jolt physics). Code comments and in-game text are in **German**; identifiers are a mix. The whole game plays on a single table surface at world **Y = 0**, viewed as a "casino table screen": 2D UI is rendered into a `SubViewport` and displayed on a mesh (see Architecture).

**Comments:** keep them to the necessary minimum — short German one-liners that state a non-obvious rule, constraint, or design decision. Don't restate what the code already says, don't duplicate a `description` string that sits one line below, and don't write essay-length narrative blocks or "siehe X" cross-reference chains. When in doubt, cut it.

## Architecture

### Layered `scripts/` — the folder IS the dependency rule
`core/` and `data/` must not import from folders below them. New scripts are placed by layer, not by feature:

- **`data/`** — `Resource` records only: `DieDefinition` (per-die faces/materials), `Charm`, `Engraving`, `Pack` (sealed shop goods), `DieMaterial`, `RoundEvent` (per-block round events). Each type's ids are `const` string constants (single source of truth) so a typo is a compile error, not a silent no-op that never matches in a `match`.
- **`core/`** — pure logic, **no Nodes** (all `RefCounted`/static): `DiceScoring` (Balatro-style hand values = base points × multiplier), `CharmEffects`/`EtchingEffects`/`MaterialEffects` (id-dispatched effect resolution), `GameRun` (the persistent run state — money, 30-die pool, charms, engravings, sealed packs, round progress; owns all economy methods and emits signals to the UI), `ScoreBreakdown`, `SlotMachine`, `SideBet`, `DiceOffer` (dice templates + refinement rolls, shared with `Pack`), `GameSettings` (volume/fullscreen in `user://settings.cfg` — the view reports changes, `scene_root` applies and saves them).
- **`dice/`** — the physical die: `DiceController` (physics of the 6 dice slots — throw/hold/rest-detection; which value shows comes from each slot's `DieDefinition`, physics only reports which physical face is up), `DieBuilder` (builds dice entirely in code — no `.tscn`), `DieFaceDisplay`, `RotatableDieView` (isolated-world drag-to-rotate preview with face/edge picking).
- **`table/`** — 3D props, camera, and the on-table screen system (see below).
- **`ui/`** — 2D panels and styling shown inside the table screen (`ShopController`, `TitleView` (title screen + pause menu), `WorkshopView` — the Werkstatt stash that opens packs and hosts `DieInspectorView` (the engraving station) via `attach_station` —, `SupplyDrawerView` (see below), `SlotBankView`, `SideBetPanel`, `CharmLibraryView`, `EngravingRenderer`, `CasinoStyle`, plus the shared builders `DiceRowView`/`CharmThumb`/`DiceGridView`/`DieNetView` — the last one is the "Würfelnetz" (unfolded-cross die dossier: cell color = face material, cell border = edge material, gold frame = face up, plus a Kanten-Chip — a tinted diamond in the empty top-left cross corner reporting the edge material) shown in the pit's compact net card via `TableScreen.set_pit_die`; hovering a face/edge writes a single-line material caption to a separate wide bar lower in the pit screen — between the net card and the pit's bottom wall (`set_pit_net_hint`/`place_pit_net_hint`), never inside the card).

### `scene_root.gd` — the single coordinator
Top-level `Node3D` (not in a subfolder). Owns exactly one `GameRun`, wires its signals to the UI, drives round flow (throw → score → take/reroll → round-goal → shop), and passes the same `GameRun` instance (typed) to `ShopController` and `DieInspectorView`, which mutate state **only** through `GameRun` methods. It also does mouse-forwarding: `_forward_screen_mouse` projects window clicks onto the table plane and `push_input`s them into the `SubViewport`; `_screen_forwards_pixel` gates which rects forward per camera mode. `_ready` is split into named setup steps (`_setup_dice`/`_setup_table_screen`/`_setup_camera_targets`/`_setup_panels`/`_setup_settings_ui`); camera raycasts go through the shared `_ray_pick(pos, mask)` helper and click zones through `_add_click_zone`.

### The table-as-screen display system (`table/`)
- **`TableScreen`** (`table_screen.gd`) — a `SubViewport` rendering 2D UI to a `ViewportTexture` on the "Screen" mesh. Its windows live inside it: `HubView` (home page + `ShopController` as an attached page), `WorkshopView`, `SlotBankView`, `SideBetPanel`, `TreasureChestView`.
- **The title HUD** — `TitleView` is a hub page like the shop and carries the start screen, the pause menu **and the game-over screen** (`Card.GAME_OVER`; `_home_card` is where `go_back()` lands, so after a loss the way back ends at the result, not at the menu). `CameraRig.Mode.TITLE` frames it: straight down (`TITLE_BASIS`, no tilt) at the distance that fits the whole hub window plus a margin (`title_distance`, `TITLE_MARGIN`), so the table stays visible around the menu — deliberately not a cover crop. Reflections are switched off there (`ScreenReflection.set_enabled`) — mirrored dice ghosted over the menu. Page changes at the title go through `HubView.fade_page_in/out/fade_current_in` (fade out, then the page rule hands the surface over, then fade in) — a hard cut showed while the camera was still travelling. "Neues Spiel" passes `fade_page_out` an `on_hidden` callback and takes over the fade-in itself: rebuilding the run costs ~0.24 s of frame time, and it has to sit in the dark moment between the two fades, never inside a fade or under the pull-back. Boot runs the normal setup and starts the round, then opens the title over it; "Neues Spiel" resets and plays `reveal_table()` (the long pull-back). Escape/the hub's Menü entry toggles it (`_toggle_title`) and it stays put on the start screen.
- **Combo chips** — every combination stands as a physical 3D chip on the **felt** (`ComboChipView`, model `assets/models/chip.glb`), wired into the LED network at its pins; there is no window under them. In `socket_mode` the 2D `ComboCellView` draws **nothing at all** — it survives purely as the data record and pixel anchor (cell center = origin of the scoring comets, cell size = basis of the wiring geometry). `ComboChipView.pin_offsets_px` is the single source for where the pins sit in screen pixels — everything docking onto them (the LED stubs, the purchase comets) derives from it instead of re-deriving the projection. The chip's **lid carries the display**: name, Basispunkte, ×Mult and the level badge ("LVL n") sit as Label3Ds flat on a glass field, because the lid is the face the overview camera sees best. Heat (= level % 5 on the cool→cyan→amber→red ramp, white-hot from 25 — every 5th level is reserved for a future cooler mount) glows in the front band, while the lid glass stays deliberately dark and capped (`SCREEN_EMISSION_MAX`) so the text never washes out. Since the cell shows nothing, the Rampenlicht also lives on the chip (`set_spotlight` = golden breath, driven by `scene_root._set_spotlight_combo`), and so does the highlight of the rolled hand: `set_glow` pulls **package, pins and band** into gold (`HIGHLIGHT_*`), which is the only way the counting combination is findable among thirteen chips. The lid glass is deliberately excluded from that gold — tinting it, plus the bloom off the golden package, swallowed its own text. The cell stays the single data source: after any `set_score`/`set_level`, `scene_root._sync_combo_chip` copies its values onto the chip — never write chip text directly.
  Two traps the model imposes: `Pins` has no UVs and `Body`'s were shredded by the Blender booleans, so surface textures must be **triplanar**; and the 45° front band leans exactly on lid height, so it needs `BAND_SEAT_DROP` or its top edge z-fights the lid into a dashed line.
- **Hub vs. Werkstatt** — the split is *buy vs. use*: the hub is the casino side (round/roadmap, money, license upgrades, shop — everything sealed), the Werkstatt is the player's workbench (opening packs, the engraving stock, applying engravings). Anything dice-shaped belongs at the workbench corner.
- **The workbench corner** — pool/discard trays on top, `WorkshopView` below them, and a row of three `SupplyDrawerView` windows under that, one per engraving category and colored like the matching shop pack. The drawers are **dual-mode on the same slots**: stock display normally, the engraving station's tool board while it's open (`set_ceremony`) — hence a fixed slot geography where unowned archetypes stay as shadows. One `CameraRig.Mode.WORKSHOP` zoom frames the whole corner, and everything in it shares **one** unit (`corner_unit` in `_setup_table_screen`), because a narrow drawer deriving `u` from its own width would render micro-type.
- **"Windows"** — each UI region (HUD/`HubView`, goal bar, dice pit) is a bordered panel with a shared `window_style()`. Outside the windows is dark-purple casino felt via `assets/shaders/table_felt.gdshader`. The combinations cluster is deliberately **not** a window: its chips stand on bare felt (see *Combo chips*), so `cluster_rect` survives only as geometry — zoom target, spill light, side-bet/slot-bank sizing, bus length — and is absent from the glass/felt `window_*` uniforms. Consequence: no glass there, hence no chip reflections.
- **Light routing (core rule)** — every comet/meteor between screens rides the laid LED-strip network (`LedStripView` paths, chained via `_route_via_strips`); nothing flies free across the felt. The combo chips hang on that same network: `combo_wiring` is one `LedStripView` carrying the whole chip net in `rail_paths`, kept deliberately sparse: only the **shared** vertical buses (`combo_bus_xs` keeps an x only if it borders two columns — the outer ones served one side each and littered the felt), ONE cross rail along the cluster's bottom edge tying them together, and per chip a single stub per adjacent bus on the middle pin row. **Both external adern must land on a corner of that net, never on open track**: the hub ader enters at the bottom-right corner (right bus × cross rail, `link_hub_to_cluster` overrides the usual center entry for exactly this), and the score ader leaves at the top of the **left** bus (`link_score_strips`) and runs the cluster's top edge — which doubles as the upper cross connection, so the right bus needs no separate top rail. Light therefore crosses the net diagonally, hub corner to score corner. The Übertaktungs-Kauf rides it via `wiring_paths_to_cell`, which only ever uses buses that are actually laid, so edge columns get two comets and the middle four. When a route has to pass a window, the light travels **along that window's border** (`_border_route`), never through a foreign screen's interior — the slot-machine → stockpile route (`slot_engraving_route`) is the reference. The round-end charm ceremony uses `_round_end_route`: charm pad → collector rail → score-window frame → pit data bus → around the pit half → hub (the bank comet's own path), then onward via the target strip (treasure strip for money, workshop + supply strip for engravings). New travel animations must compose these helpers instead of drawing direct or free-form paths.
- **Reflections** — no SSR in `gl_compatibility`. `ScreenReflection` (`screen_reflection.gd`) is a `SubViewport` with a mirror camera (main camera mirrored across the plane, negated-X basis) rendering reflection-layer (`1<<10`) instances into a texture. `assets/shaders/screen_glass.gdshader` (`render_mode unshaded`, so scene lights don't paint the glass) blends UI + masked reflection; window rects/radii are pushed into its `window_*` uniforms by `TableScreen._sync_reflection_windows()`. `ScreenReflection.mark_reflective(root)` ORs the layer bit onto `VisualInstance3D`s.
- **`CameraRig`** (`camera_rig.gd`) — overview camera tilts to follow the mouse each frame. `set_tilt_locked(true)` freezes it (used while dragging the projected die); on release it holds for `TILT_RESUME_HOLD` (0.5 s) then `smoothstep`-eases the look-around back over `TILT_RESUME_EASE` (1.0 s) rather than snapping. `release_tilt_immediately()` cuts the resume short.

### Benchmark, Stresstest & Routen-Deals
The round goal is called **Benchmark** in all UI text (never "Blind"/"Ante" — deliberately un-Balatro). Every last round of a goal block (6, 12, …) is a **Stresstest** (`GameRun.is_stress_round`), and the settlement that ends it is the **Abrechnung**.

**Routen-Deals are the progression system.** From round 2 on the player signs one of three offers (`RouteDeal`, `GameRun.route_offers`) — the **first round of a run deliberately has none** (`advance_round` rolls the offers, `new_run` does not), so the player throws once before the house starts bargaining. Each deal has a bonus and a malus with **independent durations** (`Scope.INSTANT/ROUND/BLOCK`) — that split is where the strategy lives, since a BLOCK malus costs five rounds in round 1 and almost nothing in round 5. `_scope_reaches` is the single arbiter of "is this side live"; every effect query goes through `_bonus_active`/`_malus_active`, never through raw membership. Offers use **fixed slots** (economy, gameplay, wildcard — 30 % of wildcards are the pure-bonus treats Happy Hour/Turniernacht/Spannungsspitze) plus two guards: no deal already taken this block, and never a second benchmark malus (a self-built unreachable goal is a death the player can't read). An exhausted pool falls back to repeats — an empty slot is worse. The Stresstest round swaps the whole offer for the `Slot.BOSS` pool: *how* do you want to fight.

Effects resolve **only** as `GameRun` queries dispatched on the deal id — never a silent branch in `scene_root`. `effective_goal()` inflates the stored `round_goal` (not `goal_for_round`, so a directly set goal still moves the bar) and `stage_size`/`cumulative_threshold` hang off it, which carries a benchmark malus into the bar, the overcharge stages and the win check at once. `effective_goal_for_round(n)` projects it onto the roadmap so signing visibly lifts the coming stations.

**Thermal Throttling** is the Stresstest's own threat: `hottest_combos(n)` picks deterministically at round start (level desc, tie → higher `HAND_PRIORITY`; `ONE_KIND` never, it's the fallback every hand must keep — and the tie must be broken *explicitly*, `sort_custom` is not stable). It is a **list**: Doppelbelastung throttles two chips, Kulanz none. It travels as `DiceScoring.CTX_THROTTLED` inside the same ctx every scoring call already gets, so preview, take and farkle comparison agree; `best_hand` falls through to the next matching category. The chip shows it itself (`ComboChipView.set_throttled` = red band + "AUS"). Because the boss deal is signed *before* the round, `apply_round_start_charms` sees it — that order is load-bearing.

**Where it shows.** The choice lies **in the pit** (`RouteChoiceView`, a child of `TableScreen` spanning the pit's upper part above the net field — `scene_root._place_route_choice`): the round starts normally, and the cards appear the first time the player focuses the pit that round (`_on_camera_mode_changed`, same hook as the supply tray), i.e. right before the first throw. No back, no close: while the cards lie there the **pit is shut** — `_route_choice_open()` blocks the right-click pull-back and every zoom zone (`_try_zoom_click`), and `route_pending` blocks the throw; only Escape still opens the pause menu, because a pause must never be reachable-only-by-deciding. The cards take the **whole pit floor**, so the pit's own furniture (action buttons, net field, material hint, both score orbs) hides while they show — driven from `_sync_screen_action_buttons`, which runs per frame and therefore also takes back what `update_pit_score`/`_refresh_ui` switch on in passing. The pit camera mode must forward clicks to the cards (`_screen_forwards_pixel`), which otherwise only passes the action buttons. Because the round now starts *before* the signature, the round-start effects are split out into `_apply_round_start_effects` and fire either immediately (round 1, no offers) or on signing — the boss condition must be known before the throttle is computed, and the Wartungsvertrag must grant in its own round. The view's unit derives from **both** axes (`min(w/100, h/46)`); the pit is wide and flat, so width alone would produce giant type. Active sides live on as **tokens**, and the row is **mirrored**: one `DealTokenRow` under the hub's rim and a second along the pit's upper edge, both fed the same `GameRun.active_deal_sides()` from one place (`scene_root._refresh_deal_tokens`) so they can never disagree. Grammar (owned by `DealTokenRow`, not by either host): fill = deal color, ring green/red = bonus/malus, size = duration, glyph +/−; hover opens a `HintCard` — the shared card the Stresstest station uses too, which must be a child of its stage because it positions itself stage-relative. Rebuilt whole, never patched. The Abrechnung sweeps **both** rows (`sweep_deal_tokens`/`sweep_pit_deal_tokens`, the longer awaited before the shop) and only then clears the deals.

Two rules the pit row lives by. It sits at the pit's top edge **left of center**, because the score window's data ader drops into the pit dead center — a token on that lane gets crossed by every scoring comet (`PIT_DEAL_RAIL_*`, world coords like the other pit furniture; its `u` comes from the strip height so a BLOCK token fills it to 80 %). And its hover cannot use `mouse_entered`: the pointer is on the table, not in the `SubViewport`, and outside the forwarded rects no motion ever reaches the marks — so `scene_root._sync_pit_deal_hint` asks `pit_deal_token_at(pixel)` per frame (hence `self_hover = false` there), which also means the row comes and goes with the rest of the pit furniture in `_sync_screen_action_buttons`. Roadmap markers now only ever mark the Stresstest station, tinting the **bubble itself** — a dot under the disc was invisible from the overview distance, and marked stations deliberately ignore the distance fade (the Stresstest always sits farthest).

A new deal gets its id + factory in `RouteDeal` and its effect as a `GameRun` query; a new *effect kind* also needs its call site (payout, goal, side bet, overcharge) wired through the matching query.

### Extending content
A new **charm** or **engraving** needs no registration map: add a factory method + `all()` entry in the `data/` class and its effect in the matching `core/` effects class, both wired by the same id constant. **Asset filename = content id** (`assets/models/<charm_id>.glb`, `assets/textures/engravings/<engraving_id>.jpg`); paths are derived by convention. `DieDefinition` is shared by reference — call `instantiate()` before mutating a die you take ownership of, or a later upgrade mutates every die sharing that definition.

### Scoring trigger order (fixed — NO exceptions)
There are **two charm classes**, and the class decides *when* a charm fires:

- **Die-bound charms** (`CharmEffects.die_charm_*` hooks) hang on a concrete die and fire **with that die** in the die phase — Breitband/Straßenkehrer/Zargenglanz/Bodensatz/Prime Time per combination die, Leuchtturm/Hochstapler with the highest scored die (`die_charm_target_mult_at`), Beherit's crit with the lowest (`die_charm_crit_at`). When a die fires more than once (Quecksilber, Hasenpfote & Co., Echo-Kammer — `MaterialEffects.activation_count`), its die-bound charms fire **once per activation**, interleaved: Würfel → Charm-Anteil → Krit-Schlag, then the next activation. Within one activation: eyes → material (`MaterialEffects.*_once`) → die-bound additives → die-bound crits.
- **Static charms** (`charm_*_at` hooks) depend on the hand/state, not on a single die. They fire **after all dice, strictly in ownership (dock) order** — additive bonuses AND factors (Einserkult, Feierabendbier, Galgenhumor) apply at their exact position, never pooled at the end, so dock order is gameplay-relevant. **Static crits** multiply the *current* mult (`charm_crit_at`, `crit_x` on the charm step). After the base × mult merge, total-level effects (`charm_total_factor_at` — Zauberkarte) also run in dock order.

**Die-phase order is the lined-up row and is scoring-relevant.** The sweep iterates `DiceScoring.trigger_order(scored, dice)`: value-desc, tie → smallest slot — exactly the row `_line_up_settled_dice` lays out, computed canonically from the values so preview, scoring and the pit animation always agree (no `eye_order` parameter anymore). Because Beherit's ×-crit books inside the die phase, this order *changes totals* by design (mult added after the crit die's step escapes the ×) — that's why the order must stay canonical; never derive it from physical positions. `participating_indices` still returns slot-sorted indices; Echo-Kammer/Vorreiter target the min slot via `CharmEffects.first_participating`.

**Ties on a single-die charm (fixed rule).** When a charm means exactly *one* die picked by its face value (Hochstapler/Leuchtturm = highest, Beherit = lowest, Flickenteppich = highest), a tie is broken by **the first matching die — the smallest slot**. Never scan for the extreme value yourself; call `CharmEffects.target_die(values, candidates, highest)`, the single source of truth.

`ScoreBreakdown.build` mirrors the formula 1:1: every die step carries per-activation entries (`activations`: die pulse → `charm_*_add/after` → `crit_x`/`mult_after_crit`), played by `scene_root._play_die_step`; static charm steps stay in the charm phase (`_play_crit_step` for static crits). When adding a charm, put it in the class where it belongs — a die-bound effect in the `die_charm_*` hooks, a static one in the `charm_*` hooks — or the animation fires it in the wrong phase.

The same rule holds at **round end**: after the round payout and before the shop opens, round-end charms fire strictly left to right in `scene_root._play_round_end_charm_ceremony`, and every effect is **visible** — money charms (Zinsgroschen, Überflieger, Glücksgroschen, Notgroschen) pay as **real chip denominations** (`ChipStackView.split_gain`, each packet in its chip color) launched in a dense stagger from the dock pad, every packet booking its own value on arrival; Frankiermaschine fires one meteor per engraving as a dense volley (`STAMP_METEOR_GAP` between launches, no waiting for the previous arrival), each granting on its own arrival (`GameRun.roll_stamp_engraving` rolls, the ceremony grants). All of it travels the LED-strip route through score window, pit and hub (see *Light routing*). A new round-end charm gets its case in that ceremony — never a silent mutation in `GameRun`.

## Testing notes (GUT quirks)

- **`test/unit/`** — fast pure-logic tests (no scene tree). **`test/integration/`** — tests that build nodes.
- GDScript won't auto-convert untyped array literals to the typed `Array[int]`/`Array[String]` these APIs expect — use the `_d()`/`_ids()` helpers (they `.assign()` into typed arrays). Pulling from an untyped `Dictionary` needs an explicit type (`var k: String = h["key"]`, not `:=`).
- `assert_signal_emitted_with_parameters` chokes on **bool** params (crashes in `signal_watcher.gd`/`diff_tool.gd`) — record emitted values manually via a `connect` lambda and assert the resulting array instead.
- `get_global_rect()` on freshly-built container children returns a zero rect until a frame passes — `await wait_frames(2)` before asserting layout.
- For inspector/engraving tests that apply etchings: `view.run = GameRun.new_run()` then `view.run.grant_engraving(Engraving.chisel())`.
